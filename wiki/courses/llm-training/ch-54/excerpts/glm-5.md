# GLM-5 technical report — asynchronous agentic RL infrastructure (slime)
- **Artifact:** Zhipu AI / Z.ai, GLM-5 technical report (744B parameters, 28.5T pre-training tokens; §1). Source type: official technical report. Code: github.com/zai-org/GLM-5. Read from the report text cached 2026-09-17.
- **Core Insight:** GLM-5's agentic RL runs generation and training as separate engines joined by a Multi-Task Rollout Orchestrator; stability under the resulting off-policyness comes from four concrete mechanisms — a token-in-token-out gateway, a double-sided token-level importance-sampling mask that reuses rollout log-probabilities, a staleness filter on the model-version gap, and exclusion of samples that failed because the environment crashed (§3.3, §4.1.2).
- **Guideline:** When agent trajectories span several weight updates, record the model version of every segment and drop a trajectory whose oldest segment is more than τ versions behind the current policy, and record the failure reason for every sample so that environment crashes are excluded from the reward instead of being scored as model failures (§4.1.2).

## Technical details (with loci)
- **Decoupled infrastructure (§1, §3.3, §4.1.1).** Built on the slime framework with decoupled rollout engines first used in GLM-4.5. Rollout weights are synchronized with the training engine every K gradient updates; the optimizer is reset after each weight update of the inference engine because the rollout policy has changed (§4.1.1). The orchestrator supports over 1k concurrent rollouts and dynamically adjusts task sampling ratios (§4.1.1).
- **Token-in-token-out, TITO (§4.1.2).** TITO means the training pipeline consumes the exact token stream produced by the inference engine. Text-in-text-out treats the engine as a black box returning text, which the trainer re-tokenizes. The report states that re-tokenization introduces mismatches in token boundaries, whitespace and normalization handling, truncation, and special-token placement, which can corrupt step alignment between actions and losses. A TITO Gateway intercepts generation requests and records token ids and metadata.
- **Direct double-sided importance sampling (§4.1.2, Eqs. 3-5).** In asynchronous training the rollout engine may update several times inside one trajectory, so tracking the exact `π_θ_old` would require keeping a history of checkpoints. Instead the rollout log-probability is used directly as the behavior proxy: `r_t(θ) = exp(log π_θ(a_t|s_t) − log π_rollout(a_t|s_t))`, and `L(θ) = E_t[ f(r_t(θ), ε_ℓ, ε_h)·Â_t·log π_θ(a_t|s_t) ]` with `f(x; ε_ℓ, ε_h) = x` when `1 − ε_ℓ < x < 1 + ε_h` and `0` otherwise. Tokens outside the band are removed from the gradient entirely. The report describes this as similar to IcePop but simpler because `π_θ_old` is dropped.
- **Staleness filter by version gap (§4.1.2).** For each response the sequence of model versions `(w₀, …, w_k)` with `w₀ < … < w_k` is recorded. With current version `w′`, the sample is discarded if `w′ − w₀ > τ` for a predefined threshold τ.
- **Environment-failure exclusion (§4.1.2).** Coding-agent sandboxes fail for reasons unrelated to the model. The failure reason is recorded per sample and samples that failed by environment collapse are excluded. For group-based methods such as GRPO, an incomplete group is padded by repeating valid samples when more than half the group is valid, and dropped otherwise.
- **Tail latency (§3.6.2).** Prefill-decode disaggregation runs prefills and decodes on dedicated resources so that decodes are uninterrupted and long-horizon samples keep progressing, which the report gives as the fix for tail behavior in multi-turn agentic RL.
- **Fault tolerance (§3.6.3).** Rollout servers emit heartbeats; unhealthy servers are terminated and deregistered from the inference router so retries are routed to healthy servers.
- **DP-aware routing (§4.1.2).** Requests are routed to preserve KV-cache locality under data parallelism for large MoE inference, so prefill cost grows with incremental tokens rather than total context length.
- **Environment scale (§3.3, §4.2).** Verifiable training environments across three domains: over 10K real-world software-engineering environments, terminal tasks, and high-difficulty multi-hop search tasks, plus a slide-generation environment verified by executable rendering and layout checks.
- **Synchronous-stage algorithm (§3.2).** Reasoning RL uses GRPO with IcePop to handle the training-inference mismatch, distinguishing the training policy `π_train` from the inference policy `π_infer`.

## Not reported
The values of τ, ε_ℓ, ε_h, and K; throughput numbers for the asynchronous pipeline; an ablation isolating any one of the four stabilizers.
