Elasticity in Rocket: who resizes what, and when a change takes effect

Companion to ch-21. Part 1 redraws Rocket's two-layer scheduling (Fig. 7, p. 12, from the PDF text layer) and runs resize and failure events on an illustrative node pool. Part 2 is a timeline showing where a runtime-setting change takes effect. Part 3 plots the Table 1 savings rows. Node counts, rack sizes and times in Parts 1–2 are illustrative.

1. Two-layer scheduling

Cluster scheduler (Kubernetes / Slurm)
Cluster-wide nodes, owned by the cluster: CPU nodes, GPU nodes, other nodes. Adds nodes to the job allocation.
↑ request more nodes if needed    ↓ add nodes to job allocation
Rocket job: job-wide node pool (owned by this job)
Scheduling actortracks assigned + spare nodes; topology-aware allocation; assigns nodes to components, requests nodes when suitable capacity is insufficient
Runtime configtarget size; problem mixture; other runtime settings. Learner, inference worker and controller read it dynamically
↓ assign nodes    ↑ request nodes    (components read target size)
Component-assigned nodes (owned by components within this job)
Learnerresize at checkpoint
Inference workeronline resize
Controllerreads problem distribution; CPU-only nodes (p. 12)
Spare nodesunassigned nodes in the job pool; one group sized to one learner slice

Source: Rocket p. 12, Fig. 7: "the cluster scheduler allocates nodes to the job, while Rocket assigns topology-compatible groups to components and reuses released nodes within the job." "We keep a spare group of nodes sized to replace one learner slice. If a slice fails, Rocket uses the spare group while autoscaling replenishes it."

2. When does a change take effect?

Rocket p. 12–13: "Components apply updates at defined boundaries, such as after a training step or before a sampling operation." "Inference workers can be resized immediately when new configuration comes. For the learner, we wait and only resize it after the next checkpoint save." Which setting is read at which boundary is ch-21 §4's mapping.

Illustrative timing: learner step = 12 time units, checkpoint save after every 4th step, a sampling operation (one GRPO group dispatched from one problem) every 9 units lasting 4 units.
