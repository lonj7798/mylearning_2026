B. Token-in/token-out vs re-tokenizing the final conversation (illustrative toy tokenizer)

The learner trains on token ids and the sampler's log-probs. If the trainer instead applies the chat template to the final message list and re-encodes it, the ids can differ from what was sampled ([[tito-token-in-token-out]]). This panel uses a 23-entry toy vocabulary and a greedy longest-match encoder; real BPE differs in detail but has the same three drift sources. Turn sources on and off.

trainer builds the sequence by:
1. tokens the engine sampled (id, sampler log-prob)
2. text the trainer sees after decoding and post-processing
trained ids == sampled ids (slime's end-to-end assertion)
positions where the trained id differs from the sampled id
length: sampled → trained

Effect size: no framework reports a measured accuracy effect of re-tokenization drift. verl's documentation reports that applying the chat template to the final history made PPO "not even converged in single-turn" (experience report, no numbers; [[verl-rollout]] agent_loop.rst L180–182). verl's builders treat inserted boundary tokens as "not model-generated and therefore must not carry loss or model logprobs" (continuous_token.py L38–48); in token-in/token-out mode above, the inserted newline is appended with mask 0.

metric:scale:

Inside one GRPO group (Rocket Fig. 4, p. 6–7): the slowest rollout took 784 turns, sampled from six successive weight versions, and the fastest rollout waited 7.6 h for it; each rollout waited 24 min before its first inference request. Rollouts "may hold VMs and other resources before generation starts" (p. 7), so the sandbox fleet is sized by in-flight rollouts, not by rollouts currently generating. slime's coding-agent defaults set agent / grader / whole-rollout timeouts of 3,600 / 600 / 7,200 s ([[slime-agentic-and-mismatch-examples]]).
