Distilled start vs climb from base: what changes with run length

Companion to ch-01. Numbers are quoted from [[mai-rl-infrastructure]] (cited as "Rocket p. N"), [[mai-thinking-1]], and the open reports in ch-01 §1.3. Inputs marked illustrative are not from any source; they exist to show the shape of a calculation.

1. Run length: where reported runs sit, and what accumulates per step

Rocket's argument: in a distilled start "small mismatches between sampler and learner have little time to compound"; a climb from base runs "many thousands of training steps spanning weeks to months" (Rocket p. 1). The axis below is RL steps (log scale). Step counts across runs do not compare exactly, because batch sizes and rollout lengths differ (ch-01 §1.3).

    Shaded band: 60–2,000 steps, the range of RL lengths reported by the open recipes in this library ([[areal-async-rl]] Table 1; [[olmo-3-rl-pipeline]] Table 49). ScaleRL shows open groups also run long climbs, so the boundary is not "open versus closed" (ch-01 §1.3). Rocket's Fig. 8 shows only "a portion" of its run, steps 40–2,000.

    Accumulation of a per-step sampler–learner bias (illustrative)

    No source gives a magnitude for the per-step effect. This calculator shows only the arithmetic: if each update carries a small bias ε, the total after N steps is N·ε when ε is constant. Rocket reports a "larger sampler–learner log-probability discrepancy at a later RL checkpoint than at initialization" with identical inputs, which "suggests that optimization may amplify or exploit numerical differences" (Rocket p. 9). The second curve models that case as ε doubling every D steps; D is illustrative.

    2. Failures and reconfigurations over wall-clock time: restart vs targeted recovery

    Rocket Table 1 (p. 11) covers "a portion of RL training, assuming 6,000 GPUs": 2,490 h, with 21 in-job recoveries (0.5 h saved each), 88 learner recoveries (2 h each) and 123 runtime-elasticity events (2 h each); total 432.5 h, 17.37%. Per-event savings "are estimates". This calculator applies those event rates to another run length. With 2,490 h and 6,000 GPUs it reproduces Table 1.

    Assumptions of this extrapolation: events occur at Table 1's rate per hour, and that rate scales linearly with GPU count (an assumption; Table 1 gives one GPU count only). Olmo 3's GPU count is not used here, so the Olmo presets set only the duration. Restart also has a cost Table 1 does not count: MAI-Thinking-1 reports that resuming from a checkpoint saved before a collapse "is often not viable" because instabilities are embedded "many steps before the actual collapse" ([[mai-thinking-1]] Sec. 3.1.4).
