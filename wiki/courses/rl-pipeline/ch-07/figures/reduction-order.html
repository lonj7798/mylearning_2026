A. Floating-point addition is not associative

The same effect in BF16. Edit the three numbers; each partial sum is rounded to BF16.

With the defaults, b = c = 2−8 is half of BF16's spacing just above 1 (2−7; next value above 1 is 1.007812 [[fp16-train-infer-mismatch]] Table 1). Adding one of them to 1 rounds back to 1 (tie to even); adding their sum does not. Summing 8 numbers in 10,000 random orders gave 102 distinct float results in the Thinking Machines post.

B. Attention output projection: row-parallel TP vs Rocket fix 1

One output element of o_proj for one token: y = Σi hi·wi over d = 64 concatenated head dimensions. Three ways to compute it:

  • Learner, no TP (Rocket's learner): one GPU, FP32 accumulation in a fixed order, output cast to BF16.
  • Sampler, row-parallel TP: each rank sums its own slice of heads, writes a partial in the chosen dtype, then an all-reduce adds the partials across ranks in the chosen order.
  • Sampler, Rocket fix 1: all-gather the head outputs h (a copy, no arithmetic), replicate Wo, compute the full sum on one GPU with the learner's kernel order [[mai-rl-infrastructure]] p. 10.

Model assumptions: the all-reduce adds in the tensor dtype; real collectives choose order by algorithm, chunking and topology [[nemo-rl-tp-accuracy]]. TP = 1 reproduces the learner exactly. Switching to FP32 partials reduces how often the final BF16 value differs but does not remove it, because grouping still differs. The fix matches by construction only if the single-GPU kernel uses the same accumulation order as the learner's kernel, which is what Rocket's shared kernels ensure.

C. MoE expert combination: arrival-order BF16 vs Rocket fix 2

A token routed to k experts needs Σe ge·Ee(x). If outputs are accumulated in BF16 in the order they arrive from the all-to-all, the result depends on arrival order. Rocket returns all expert outputs to the token's source device and computes the weighted sum locally in FP32 [[mai-rl-infrastructure]] p. 10; slime's GLM-5 path does the same "in slot order and FP32" (reproducibility.md L63–66).

D. Decode attention split-KV: split count vs fixed split size (Rocket fix 3)

One query attends to L cached tokens with online softmax. The learner's forward reduces over KV tiles of fixed size T. The sampler's decode kernel splits KV into chunks and combines them. If it uses a fixed number of splits (chosen from occupancy), chunk boundaries move with L and differ from the learner's tiles; with a fixed split size equal to the learner's tile, boundaries coincide [[thinking-machines-nondeterminism]]; Rocket tunes KV tokens per split once and uses the same boundaries in learner forward, prefill and decode [[mai-rl-infrastructure]] p. 10.

Reading the result: different split boundaries change the low FP32 bits of almost every output; most of those differences disappear when the output is cast to BF16, but a few elements flip. A flipped element is an input difference for every later layer, and a model has thousands of such elements per token per layer, so rare flips are enough to make the two engines' log-probabilities differ. The Thinking Machines example: KV length 1,000 with split size 256 gives chunks 256, 256, 256, 232 regardless of load; four fixed splits give 250 each. Set L = 1000, T = 256, mode "fixed split size" to reproduce it.
