### Q1 — what is HuggingFace's GOLD — a library?

**Not a library — a *method*, implemented as a trainer inside HuggingFace's `TRL` library.**

- **GOLD = General On-Policy Logit Distillation** (HF H4 recipe "Unlocking On-Policy Distillation for Any Model Family").
- **Where it lives:** `GOLDTrainer` in `trl.experimental.gold` (TRL = Transformer Reinforcement Learning). Hierarchy: **TRL (library) → GKDTrainer / GOLDTrainer (trainers)**; GOLD extends GKDTrainer.
- **What it does:** removes vanilla GKD's same-tokenizer requirement → a **cross-family/cross-tokenizer teacher can grade a student's on-policy rollouts** (= ch-05 Q2 solution (c)). Method: align on **visible text** (not token IDs), **merge probabilities across mismatched token boundaries via chain rule** `P_merged(y)=P(y|ctx)·P(t₁|t₀,ctx)·…`; extends **ULD** (Universal Logit Distillation, Boizard et al. 2024) to on-policy (sorted + L1 loss, no normalization needed).
- **API:** inherits `beta`/`lmbda`/`seq_kd` from GKDTrainer; adds `use_uld_loss=True` + `teacher_tokenizer_name_or_path`; experimental, default `learning_rate=1e-7`.
- **Payoff:** recovered 60% of teacher performance (ULD 10%), +20% over GRPO cross-tokenizer.
- **boson (Fork 1):** large Qwen teacher (same tokenizer) → plain `GKDTrainer`; Claude teacher (different tokenizer) → GOLD/ULD.

**One line:** GOLD = General On-Policy Logit Distillation — not a library but an experimental `GOLDTrainer` in HF `TRL`; extends ULD to on-policy so a cross-tokenizer teacher grades the student (visible-text align + chain-rule prob merge). See read.md §2, [[hf-trl-gkd-recipe]], [[ch-05]] qa Q2.

### Q2 — why is `lmbda`=0 offline and `lmbda`=1 fully online?

Because λ is the **mixing coefficient between two data sources** in the GKD loss — literally the fraction of each batch that is student-generated.

`L_GKD = (1−λ)·E_{y~D}[D(p_T‖p_S)] + λ·E_{y~p_S}[D(p_T‖p_S)]`

- **First term `(1−λ)`, `y~D`:** sequences pulled from a **fixed, pre-collected dataset** — nothing generated during training → **offline / off-policy**.
- **Second term `λ`, `y~p_S`:** sequences **freshly generated by the current student** each step → **online / on-policy**.

| λ | batch | ch-01 data-source axis |
|---|-------|----------------------|
| `0.0` | 100% fixed dataset | off-policy KD (offline) |
| `0.5` | half/half | GKD default |
| `1.0` | 100% student rollouts | fully on-policy distillation |

- **"offline/online" ≡ "off-/on-policy" here** — both name the [[ch-01]] **data-source axis** (who generated the data / whose state-visitation distribution). offline = read a static buffer, no fresh generation; online = resample from the live policy every step. λ just makes that axis a continuous 0→1 dial.
- **λ moves only the data-source axis.** geometry (forward↔reverse KL) is the separate `beta` knob — the two axes are independent (ch-01). `seq_kd=True, lmbda=0.0` = λ pinned to the fully-offline end = the [[ch-02]] Kim & Rush seq-KD corner.

**One line:** λ = fraction of the batch that is student-generated; λ=0 → all fixed-dataset (offline/off-policy), λ=1 → all fresh student rollouts (online/on-policy) — the ch-01 data-source axis as a continuous knob, orthogonal to `beta`'s geometry. See read.md §1, [[ch-01]] qa Q4, [[ch-02]] qa (seq-KD corner).

### Q3 — do you start off-policy (low λ) and ramp to on-policy (λ→1) over steps?

Direction right; **form wrong.** The standard practice is a **discrete 2-stage pipeline**, not a continuous per-step λ anneal.

```
Stage 1 (warmup):  off-policy — get student to "coherent-but-flawed"   (λ=0 region, or a separate SFT)
        ── hard switch ──
Stage 2 (OPD):     high λ (→1), fixed — on-policy distillation
```

- **`lmbda` is a fixed per-run hyperparameter** (default 0.5); GKDTrainer has **no built-in schedule**. Docs recommend keeping λ **high** once doing OPD, not ramping it.
- **Why warm up off-policy first** (= the learner's own ch-03 insight, "garbage → SFT first, then on-policy"): a too-weak student produces **garbage rollouts**; grading garbage gives weak signal AND wastes the teacher forward pass (§3 cost center). Warm up cheaply off-policy to a state worth grading, *then* go on-policy.
- **Why not stay off-policy:** that leaves [[ch-03]]'s exposure bias / compounding error unfixed — off-policy never grades the student's own drifted states. Warmup's job is only to create a usable on-policy starting point.
- **Two precision points:** (1) **don't over-warmup** — too much SFT wastes the on-policy budget and over-commits the student to mode-covering habits; spend *most* of the budget on-policy. (2) **warmup flavors:** plain SFT (hard target) vs `lmbda=0.0` off-policy KD (teacher soft target = richer, gives ch-02 dark knowledge).

**One line:** yes off→on, but as a **discrete SFT-warmup → high-λ OPD handoff** (λ fixed within each stage), not a continuous λ ramp; warm up off-policy only enough to escape the garbage regime, then spend the budget on-policy. See read.md §1/§3, [[ch-03]] qa Q8, [[ch-02]] (soft vs hard).

### Q4 — does "warm up until the student is coherent" mean training to a specific loss value?

**No — and loss is actually a *bad* stop criterion here.**

- **What "coherent" means:** a property of the student's **on-policy rollouts** (are they worth grading?). But warmup loss is **off-policy loss** — it measures fit to the fixed dataset, NOT the quality of the student's own generations. This is exactly the [[ch-02]]/[[ch-03]] reason OPD exists: off-policy loss is blind to the student's own state distribution → a given loss value doesn't certify "rollouts are now coherent." (Plus absolute loss scale isn't a universal threshold across setups.)
- **What actually stops warmup** (most→least common): (1) **fixed budget** — "SFT N steps / 1 epoch, then switch"; simplest, accepts no crisp boundary is needed; (2) **rollout-quality eval** — generate from the student, check held-out task accuracy / coherence; the only thing that directly measures "does it make sense" (look at *generations*, not loss); (3) **val-loss plateau** — a diminishing-returns signal ("stop wasting warmup compute"), NOT a coherence-achieved signal.
- **Practical:** the boundary needn't be sharp — GKD at `lmbda=0.5` already blends off/on, so unless the student is extremely weak you can start with mixed λ. And per Q3, over-warmup is waste → the answer to "until when?" is usually "the minimum point where rollouts become gradeable," then yield the rest to on-policy.

**One line:** not a loss threshold — "coherent" = the student's on-policy rollouts become worth grading, judged by a fixed step budget or a rollout-quality eval, never by off-policy training loss (which is blind to the student's own states — the very reason OPD exists). See read.md §1/§3, [[ch-02]], [[ch-03]].

### Q5 — so: warmup SFT on my own data, then fix λ=1?

**Right shape, and correct for boson specifically** — but "just fix λ=1" hides one infra prerequisite.

- **Why the plan's logic is right (boson):** the data you have = boson exported transcripts (teacher beam-search / predefined-scenario) = **off-policy**. Warmup SFT → coherent student ✅. Those transcripts *alone* can't fix [[ch-03]] compounding error (they never show the student's own drifted states), so λ=1 → the teacher grades the student's *own* rollouts → drift corrected ✅. Config AND rationale line up.
- **Hidden prerequisite — warmup and λ=1 have different cost structures:** warmup needs only static data, no teacher. **λ=1 = run a live teacher every step** to score fresh student rollouts per-token (§3 cost center). So the λ=1 stage requires: (1) a **live queryable teacher** serving per-token logprobs; (2) teacher **stronger** than student (§5 prereq); (3) **same tokenizer** (large Qwen → direct) or **GOLD** (Claude → cross-tokenizer, [[ch-05]] Q2 / Fork 1). "Just my data" is true for warmup, not for λ=1.
- **Two precisions:** (a) docs recommend **high** λ; λ=1.0 = pure on-policy (read §6 "lmbda→1" for a long-horizon agent), though some keep λ slightly <1 as a ground-truth anchor (optional). (b) warmup flavor: if the teacher is already up, do warmup as `lmbda=0.0` off-policy KD (soft, richer) instead of hard SFT (Q3); hard SFT if you only have text.
- **Still undecided (→ ch-07 capstone):** λ=1 fixes the *knob*, not the domain engineering — **which tokens actually get graded** in a tool-call/compaction/barge-in conversation, and how the existing **relay becomes the on-policy rollout environment**.

**One line:** yes — off-policy warmup SFT then high/1.0 λ OPD is the standard shape and correct for boson (transcripts warm up, λ=1 fixes the drift they can't), but λ=1 quietly requires a live stronger same-tokenizer-or-GOLD teacher serving per-token logprobs every step; which tokens to grade + relay-as-rollout-env is the ch-07 capstone. See read.md §1/§3/§6, [[ch-03]], [[ch-05]] qa Q2.

### Q6 — so it's good to just keep an SFT warm-up model on hand?

**Yes — decoupling warmup from OPD is the right engineering split** (same shape as RLHF's "SFT base → PPO", here "SFT base → OPD").

- **Why decouple:** warmup SFT is **teacher-free + cheap** (make once); OPD (λ=1) is the **teacher-dependent + expensive** stage where you iterate teacher/λ/β. A fixed warm base lets you swap the OPD stage without re-paying warmup each time.
- **Precision 1 — it's a starting point, not a deliverable.** The SFT warm model is still **off-policy** → carries [[ch-03]] exposure bias; its only value is "coherent enough to start on-policy from." Don't ship it as-is.
- **Precision 2 — it's also your baseline.** For OPD to have earned its keep it must **beat the SFT-only model on the deployment distribution** — exactly [[ch-05]] §4's "OPD student beats its own SFT teacher." Keeping the warm checkpoint gives you that measuring stick.
- **boson — you likely already have it:** the current SFT seller (Qwen trained on transcripts) *is* the warm base. So no from-scratch warmup needed; OPD is the **next stage on top**, and that existing SFT seller doubles as the baseline OPD must beat.

**One line:** yes — keep the SFT checkpoint as a reusable, teacher-free warm base (and OPD's baseline), but it's a starting point not a deliverable (still off-policy); for boson the existing transcript-SFT seller already IS that warm base, so go straight to OPD design (ch-07). See read.md §1/§6, [[ch-03]], [[ch-05]] §4.

### Q7 — what's the difference between GOLD and ULD?

**ULD = the cross-tokenizer distance itself (a loss primitive), off-policy. GOLD = that ULD loss lifted into the on-policy loop + the alignment machinery to run it on generated rollouts.** GOLD *extends* ULD.

**ULD (Universal Logit Distillation, Boizard et al. 2024) — the foundation:**
- **Problem:** different vocabularies → teacher/student per-token logit vectors aren't aligned (different dims, different token-id meanings) → [[ch-04]]-style position-by-position KL is impossible.
- **Trick — sort + L1:** at each position, **sort** both distributions' probabilities and compare the *sorted* distributions by **L1 distance**. Sorting drops token identity → compares distribution **shape** only → **vocabulary-agnostic** ("3rd-ranked prob vs 3rd-ranked prob", not "'없지' vs '없구요'"). No normalization needed (intentionally unnormalized).
- **Limit:** originally **off-policy/supervised** — both score the *same fixed-dataset text*; doesn't cover the on-policy case (student generates, teacher grades its fresh rollouts).

**GOLD (General On-Policy Logit Distillation, HF H4) — the on-policy extension:**
- Puts the ULD loss inside **GKD's on-policy machinery**, plus two additions: (1) **text-level alignment** — incrementally decode, group runs with the same **visible text**, merge probabilities by **chain rule** (`P("12")=P("1")·P("2"|"1")`) so loss covers the full completion even when token boundaries differ (the piece ULD lacked for generated sequences); (2) **hybrid** — exact vocab matches compared directly, sorted-ULD fallback for the rest.
- **Payoff:** 60% teacher recovery (ULD 10%), +20% over GRPO cross-tokenizer. `GOLDTrainer` inherits GKD's beta/lmbda/seq_kd + adds `use_uld_loss`/`teacher_tokenizer_name_or_path`.

**Mnemonic (course spine):** **GOLD : ULD  ==  OPD : off-policy KD** — both solve the same *geometry* problem (cross-tokenizer alignment) but split on the [[ch-01]] **data-source axis**: ULD = off-policy (same fixed text), GOLD = on-policy (student rollouts) + text-merge machinery. GOLD is "ULD moved to on-policy," the same off→on axis seen all course.

**One line:** ULD = vocabulary-agnostic cross-tokenizer loss (sort+L1), off-policy; GOLD = ULD lifted into the on-policy loop + visible-text grouping / chain-rule prob-merge to run it on student rollouts — GOLD:ULD :: OPD:off-policy-KD (same cross-tokenizer geometry, flipped data-source axis). See read.md §2, [[ch-01]] data-source axis, [[ch-05]] qa Q2.
