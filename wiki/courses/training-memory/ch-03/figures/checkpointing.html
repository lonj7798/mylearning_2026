Gradient Checkpointing — checkpoint은 정확히 뭘 저장하는가

ch-03 §1–§2 companion · qa.md Q1/Q2 시각화 · 한 줄 답: checkpoint = activation tensor 딱 하나, segment로 들어가는 hidden state [B, T, h]. weight도 gradient도 "layer"도 아니다.

헷갈리기 쉬운 것 세 가지. ① checkpoint은 weight가 아니다 — weight는 어차피 항상 메모리에 있고 recompute 대상이 아니다. ② gradient도 아니다 — gradient는 backward가 만들어내는 출력이지 저장해 둔 입력이 아니다. ③ "layer를 저장한다"가 아니다 — 저장되는 건 layer(module 객체)가 아니라 그 layer로 흘러들어가는 숫자 덩어리 하나, 즉 [B, T, h] shape의 tensor 한 개다. 이 값 하나만 있으면 그 아래 14개는 forward를 다시 돌려 전부 복원된다 — 그래서 버릴 수 있다.
진짜 괴물은 attention이다. [B, a, T, T]는 T에 제곱으로 커진다 — T=4096에서 1.07 GB, T=8192면 4.29 GB. 그런데 이걸 다시 만드는 비용은 matmul 한 번 + softmax 한 번뿐이다. 저장 비용은 최악, 재계산 비용은 최선 — §3 selective recomputation이 정확히 이 비대칭을 노린다.

주: 위 목록은 dropout = 0 (요즘 LLM pretraining의 기본)에 head 하나짜리 s×s tensor 한 개만 센 보수적 집계다. read.md §1의 Korthikanti 공식 s·b·h·(10 + 24/t + 5·a·s/(h·t))은 softmax의 입력·출력·dropout mask까지 세서 같은 config에서 block당 3.25 GB가 나온다. 어느 쪽으로 세든 결론은 같다: checkpoint 33.55 MB는 그 안에서 반올림 오차 수준이다.

3 · 왜 하필 √n — memory = k + n/k를 직접 밀어보기

왼쪽 끝 = k = 1 (segment 하나) · 오른쪽 끝 = k = n (tensor마다 저장)
boundaries = k
—
저장해 둔 checkpoint 수
live = n/k
—
한 segment 재계산 window
memory = k + n/k
—
—
k + n/k 최소점 k = √n 양 끝 (k=1, k=n) ≈ n
양쪽 끝이 똑같이 나쁘다 (qa.md Q2). k = 1 → boundary는 1개인데 live window가 전부다. k = n → live는 1인데 boundary가 전부다 — 전부 저장한다는 건 아무것도 안 버렸다는 뜻인데 +33% recompute는 그대로 낸다. 순수 손해. k + n/k는 양방향으로 벌을 준다.

미분: d/dk (k + n/k) = 1 − n/k² = 0 → k = √n. 두 항이 정확히 같아지는 지점이라 최소가 된다 — 임의로 고른 숫자가 아니다.

4 · 실무: transformer block마다 — 이건 k = n이 아니다

"layer마다 checkpoint"는 방금 본 쓸모없는 오른쪽 끝인데, 실제 framework는 전부 block마다 checkpoint을 건다. 모순처럼 보이는데 아니다 — n이 세는 건 block이 아니라 activation tensor이기 때문이다. §1에서 봤듯이 block 하나에 tensor가 ~20개 들어 있으므로, block 단위 checkpointing = 크기 20짜리 segment다.

80-block model의 실제 n
n = 80 blocks × 20 tensors = 1600
block이 아니라 tensor를 세야 k + n/k가 성립한다
schemek (segments)segment 크기k + n/k
segment 하나116001601
이론 최적 k = √1600404080
block마다 (실무)8020100
tensor마다 (k = n)160011601
100 vs 80 — 최적 대비 25%밖에 안 나쁘다. 그 대가로 얻는 건 torch.utils.checkpoint(block, x) 한 줄짜리 구현이다. √n 최적 분할은 tensor 경계를 block 중간에서 끊어야 해서 module 구조를 부수고 재계산 로직을 손으로 짜야 한다.

우연도 아니다. block 하나의 tensor 수(~20)가 전형적인 모델 크기에서 √n(~40)과 같은 자릿수에 떨어진다. 자연스러운 module 경계가 구조적으로 최적점 근처에 놓여 있어서, 게으른 선택이 거의 최적이 된 것 — 그래서 이게 default가 됐다.
실제 절감량으로 환산하면 (§1의 config, 80 blocks):
checkpointing 없음 = 134.2 GB · block마다 checkpointing = 2.68 GB — 50×.
뒤 숫자는 read.md L110의 2·s·b·h·L 공식과 정확히 일치한다: 2×4096×1×4096×80 = 2.68 GB. 그 공식의 정체가 바로 "block 입력 tensor 80개"다 — §1 목록의 1번 항목 × 80.

5 · 코드 — 그리고 PyTorch가 실제로 하는 일

# 실무 형태: transformer block 하나를 통째로 감싼다
from torch.utils.checkpoint import checkpoint

class Model(nn.Module):
    def forward(self, x):
        # x: [B, T, h]  <- 이 tensor가 checkpoint 된다
        for blk in self.blocks:
            if self.grad_ckpt and self.training:
                x = checkpoint(blk, x,
                               use_reentrant=False)
            else:
                x = blk(x)
        return x

# HuggingFace는 같은 걸 한 줄로
model.gradient_checkpointing_enable()
인자로 넘긴 x가 곧 checkpoint이다. 이 함수가 "저장"하는 건 blk도 아니고 blk의 weight도 아니고, 넘긴 입력 tensor다 — §1 목록의 1번, 33.55 MB짜리 [B, T, h] 딱 하나. (use_reentrant=False가 요즘 권장값 — 재진입 방식이 아니라 autograd graph에 정식으로 붙어서 .grad 전파와 nested 사용이 정상 동작한다.)

왜 +33%인가. 재계산은 layer마다가 아니라 segment마다 정확히 한 번이다. √n개 segment × 크기 √n = n = forward pass 딱 한 번 분량 (read.md L92).
transformer의 forward : backward ≈ 1 : 2이므로
(1 + 2 + 1) / (1 + 2) = 4/3 = +33%
Chen 2016의 1,000-layer ResNet 실측: 48 GB → 7 GB (6.8×), runtime +30% (read.md L96–99). 이론값 +33%와 거의 일치한다.
