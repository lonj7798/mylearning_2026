KV Cache 완전 해부 — 왜 가능한가 · 얼마인가 · 왜 학습엔 없는가

ch-extra companion · 한 줄 요약: KV cache는 causal mask가 강제하는 memoization이고, 크기는 2 · B · s · L · n_kv_heads · d_head · bytes로 s에 선형이며, training에는 0 byte다.

1 · 왜 cache가 애초에 가능한가 — cache 없이 6 token 생성해보기

d_model = 4d_head = 2 W_K, W_V = 4×2 정수 행렬생성 길이 N = 6 손으로 검산 가능한 크기

autoregressive 생성은 token을 하나씩 뱉는다. 그런데 cache가 없으면 매 step마다 지금까지의 모든 position에 대해 K와 V를 처음부터 다시 계산한다. 아래 격자에서 파란 칸은 이번 step에 처음 계산된 값, 빨간 칸은 직전 step과 bit 단위로 똑같은 값을 또 계산한 것이다.

누적 낭비

불변식(invariant) — 이게 KV cache의 전부다. causal mask는 M[i,j] = −inf (j > i)이다. 그래서 k_j = W_K x_j, v_j = W_V x_j는 오직 token j 하나에만 의존하고, x_j 자신도 position ≤ j 에만 의존한다.

따라서 token t+1을 뒤에 붙여도 k₁..k_t, v₁..v_t 는 하나도 바뀌지 않는다. 과거의 K, V는 immutable이다 → 다시 계산하는 건 순수한 낭비다. cache는 영리한 트릭이 아니라, 이미 pure function인 것에 대한 memoization일 뿐이다.

거꾸로 말하면: bidirectional attention(encoder)에는 KV cache가 없다. 거기선 뒤 token이 앞 token의 표현을 바꾸므로 k_j가 immutable하지 않다. KV cache를 가능하게 하는 건 causality이지 attention이 아니다.

2 · cache를 붙이면 — 같은 생성, 나란히 비교

왼쪽은 §1과 똑같은 no-cache 정책, 오른쪽은 cache에 한 줄씩 append하는 정책이다. 같은 token을 뱉고 수치 결과도 완전히 동일하다 — 다른 건 오직 계산량뿐이다. 아래 attention 계산은 실제 정수 내적을 그대로 보여준다.

왜 이게 정확히 O(N²) → O(N) 인가. token을 N개 생성할 때 "token 하나에 대한 forward pass" 횟수를 세면, cache 없음 = 1+2+…+N = N(N+1)/2, cache 있음 = N. 비율은 (N+1)/2다.

FLOP으로 세도 결론은 같다 (layer 하나, B=1, d=8192 기준, 아래 표는 정확 합산): prefill/decode 원가 7·B·d² + 2·B·t·d를 t=1..N으로 더한 값이다.

비율이 N에 선형으로 커진다는 게 핵심. 그리고 실측(Raschka, 124M 모델, 200 token, Mac Mini M4 CPU): no cache 17.5 s → naive cache 3.3 s (5.3×) → pre-allocated 2.8 s (6.25×) → + torch.compile 2.4 s (7.3×). 작은 모델·짧은 생성이라 이론 배수보다 훨씬 작다 — 이론 배수는 N이 커야 나온다.

3 · prefill vs decode — 같은 weight, 완전히 다른 병목

한 request는 두 개의 서로 다른 기계를 연달아 돌린다. prefill은 프롬프트 전체를 한 번의 병렬 pass로 밀어넣고, decode는 token을 하나씩 뱉으면서 매 step 모든 weight와 cache 전체를 다시 읽는다.

모델 = Llama-3-70B급P = 70e9 params bf16 → weights 140 GBprompt T = 4,096 L = 80, n_kv = 8, d_head = 128B = 1
roofline = min(peak, BW × I) prefill · I ≈ 3,100 decode(B=1) · I ≈ 0.3 knee · I = 590
왜 decode가 bandwidth-bound인지 — 직관 한 줄. arithmetic intensity(FLOPs/byte)는 결국 "weight를 한 번 읽어서 token 몇 개를 처리하느냐"이다. weight 하나를 읽으면 곱셈-덧셈 2 FLOP을 쓰므로, T개 token을 한 번에 밀면 2·P·T FLOPs / 2·P bytes = T FLOPs/byte — intensity ≈ T다.
· prefill T=4,096 → intensity ≈ 4,096 (실측 기준선 ~3,100). knee 590보다 훨씬 위 → compute-bound.
· decode B=1, token 1개 → intensity ≈ 1 (실측 기준선 ~0.3). knee 590보다 훨씬 아래 → bandwidth-bound.

실측 기준선이 이론값보다 낮은 이유는 weight 말고도 KV cache 재읽기, attention 자체의 트래픽, non-GEMM 연산(norm/softmax/rope), kernel launch 오버헤드가 전부 byte만 늘리고 FLOP은 별로 안 늘리기 때문이다.

결론적으로 batch가 유일한 탈출구다. B개 request를 함께 decode하면 weight 한 번 읽고 B개 token을 처리하니 intensity ≈ B. knee가 590이므로 B ≈ 590쯤 되어야 비로소 compute-bound에 닿는다 — 그런데 B를 키우면 KV cache가 B에 비례해 커진다(§4). 이 긴장이 serving 시스템 설계 전부다.
숫자로 못박기. H100 SXM 하나: peak bf16 1,979 TFLOPS, HBM 3.35 TB/s → knee = 1979/3.35 = 590 FLOPs/byte. decode가 I = 0.3이면 달성 가능한 연산량은 3.35e12 × 0.3 = 1.005 TFLOP/s — peak의 0.051%다. GPU가 놀고 있는 게 아니라 메모리에서 숫자가 안 올라온다.

이 그림이 이 figure에서 가장 중요한 대비 중 하나다. log–log에서 기울기가 곧 지수다. KV cache는 기울기 1(선형), 학습 때의 attention score tensor [B, a, s, s]는 기울기 2(제곱)다.

s = 131,072 에서: KV cache(70B, B=1) = 40.00 GiB. 같은 길이의 학습 attention tensor(a=32, L=80, bf16) = 80 × 32 × 131,072² × 2 = 87,960,930,222,080 B ≈ 80 TiB. 2,048배 차이다.

그래서 문제의 성격이 완전히 다르다: 긴 context serving은 "선형이지만 큰" 메모리를 어떻게 나눠 쓰느냐(paging, quantization, GQA)의 문제이고, 긴 context 학습은 애초에 그 제곱 tensor를 물리적으로 만들지 않는 kernel(FlashAttention, ch-05)의 문제다.

공식이 무엇에 의존하지 않는지가 더 중요하다. n_heads도 d_model도 식에 없다. 오직 L × n_kv_heads × d_head다. 그래서 Llama-3는 8B → 405B로 parameter가 50배가 되는 동안 KV cache는 516,096 / 131,072 = 3.9375, 즉 3.9배밖에 안 늘었다 — n_kv_heads = 8이 전 사이즈에서 고정이고 L만 32 → 126으로 늘었기 때문이다.

5 · MHA vs GQA vs MQA — 숫자 하나(n_kv_heads)만 다르다

query head는 8개로 고정이고 KV head 개수 G만 바꾼다. query head h가 읽는 KV head는 h // (H_q / G)다. FLOP은 거의 그대로인데(KV head를 query head 수만큼 broadcast해서 쓴다) cache만 H_q/G 배로 줄어든다 — 그래서 공짜에 가깝다.

MLA는 공식이 다르다 — 앞의 2가 없다. MLA bytes/token = L · (d_c + d_rope) · bytes_per_element. K와 V를 각각 저장하는 게 아니라 latent c_KV 하나가 둘을 동시에 만들어내기 때문에 factor 2가 사라진다. DeepSeek-V3: 61 × (512+64) × 2 = 70,272 B = 68.6 KiB/token. 같은 geometry의 naive MHA(61 layer × 128 head × 128 d_head)는 2 × 61 × 128 × 128 × 2 = 3,997,696 B = 3.81 MiB/token → 압축비 3,997,696 / 70,272 = 56.9×.

d_rope = 64가 압축되지 않고 남는 이유: RoPE는 position에 의존하는 회전이라 압축 전에 회전을 걸면 latent가 position-specific이 되어 재사용이 깨진다. 그래서 비용이 d_c가 아니라 (d_c + d_rope)다.
여기서 학습 쪽으로 넘어갈 때의 함정. GQA의 나눗수 H_q/G는 inference KV cache에는 100% 적용되지만 training activation에는 그렇지 않다. FlashAttention backward는 Q, K, V, O와 logsumexp 통계를 들고 있는데 GQA는 K와 V만 줄이고 Q는 그대로다.
training QKV-activation 나눗수 = 3·H_q / (H_q + 2·H_kv):
· Llama-3-8B (32 → 8): inference 4.0× vs training 2.00×
· Llama-3-70B (64 → 8): inference 8.0× vs training 2.40×
· MQA (64 → 1): inference 64.0× vs training 2.909× — 아무리 공격적으로 줄여도 3배를 못 넘는다.

검산 (B=1, s=8,192, d_head=128, bf16, 70B, layer 1개): GQA-8은 Q 128 MiB + K 16 MiB + V 16 MiB = 160 MiB/layer → 80 layer = 12.5 GiB. MHA-64는 128×3 = 384 MiB/layer → 30.0 GiB. 비율 30.0/12.5 = 2.4×. ✓

6 · 경계선 — training에는 KV cache가 없다 (0 byte)

이 figure에서 가장 중요한 패널이다. training OOM 분석에 "KV cache" 줄이 들어 있으면 그건 이중 계산이다. 이유는 하나: teacher forcing.

함정 — 대수식이 글자 하나까지 똑같다. training forward pass 중에 K와 V가 차지하는 byte는 2 · B · s · L · n_kv_heads · d_head · b — inference KV cache 공식과 완전히 동일하다.
Llama-3-8B geometry, B=1, s=8,192, bf16: 2 × 32 × 1 × 8192 × 8 × 128 × 2 = 1,073,741,824 B = 1.00 GiB — 8k request 하나의 inference KV cache와 숫자까지 같다. (70B면 양쪽 다 2,684,354,560 B = 2.50 GiB.)

그런데 전혀 다른 물건이다. training 쪽 1.00 GiB는 backward를 위해 저장된 activation이고, gradient checkpointing을 켜면 사라진다(재계산으로 대체). inference 쪽 1.00 GiB는 다음 step이 읽을 상태라 절대 못 지운다. 같은 산수, 다른 존재론 — 이 구분을 놓치면 ledger가 두 번 청구된다.
왜 PagedAttention(ch-06)은 training을 못 돕는가. PagedAttention은 KV pool의 단편화를 푸는 기법이다 — 16 token 단위 block, sequence별 block table, copy-on-write prefix 공유로 KV 이용률을 >96%까지 올린다 (연속 할당 방식은 20–38%).

그런데 training에는 그 단편화가 애초에 존재하지 않는다. 할당 shape이 step 시작 전에 이미 확정된 하나의 연속 tensor이고, step이 끝나면 통째로 해제되며, 생성 길이를 예측할 필요도 없다. 풀 문제가 없으니 해법도 필요 없다. PagedAttention은 순수 inference 기법이다.
boson / Lina TMR 에 붙여 읽기. GDN linear-attention layer는 CP=1로 hard-assert되어 있고, 그 layer의 inference 상태는 head당 고정 크기 recurrent state(표준 linear attention이면 d_head × d_head 행렬)라 sequence length에 무관하다 → 그 layer들에는 2·L·n_kv·d_head·s·b scaling 논리가 아예 적용되지 않는다.

하지만 학습 쪽은 그대로다: GDN block도 backward를 위해 position별 activation을 저장한다. 그래서 32k sequence 학습에서 터지는 건 cache 문제가 아니라 checkpointing 문제다 (ch-03). inference 최적화 문서를 학습 OOM에 그대로 가져다 쓰면 안 되는 이유가 정확히 이것. 
# training — KV cache가 들어갈 자리가 없다
logits = model(x[:, :-1])          # x: [B, s]  →  단 한 번의 forward
loss   = CE(logits, x[:, 1:])      # 모든 position에서 동시에 loss
loss.backward()                    # 저장해둔 activation 소비
opt.step(); opt.zero_grad()        # → activation 전부 해제. 다음 step은 새 batch
#  재사용할 "이전 step"이 없다 → 캐시할 대상 자체가 존재하지 않는다

# inference — 여기서만 cache가 의미를 가진다
kv = model.prefill(prompt)          # [2, B, s0, L, n_kv, d]  ← 여기서 태어난다
for _ in range(N):
    tok, kv = model.decode(tok, kv)  # 매 step 한 행 append, 절대 재계산 안 함
# 흔한 버그 2개
#  (1) 생성이 끝나면 kv를 반드시 리셋 — 안 하면 새 prompt가 이전 sequence의 key에 attend한다
#  (2) position id를 따로 추적 — pos_ids = arange(cur, cur+seq_len).
#      안 하면 새 token이 매번 position 0으로 취급돼 RoPE가 깨진다
