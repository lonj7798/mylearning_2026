Architecture Experiment Design Workflow

Click each phase to expand details and examples. References: OLMo 2, Flash Attention, Chinchilla, DeepSeek-V3.

1
Observe Bottleneck
Profile the system. Identify a specific, measurable gap between current and achievable performance.
Key questions: Where is compute wasted? Where is memory the constraint? What is the gap between actual and theoretical throughput?

Tools: GPU profilers (NSight, PyTorch Profiler), memory breakdowns, roofline analysis, arithmetic intensity calculations.
Flash Attention: "Standard attention achieves 25-40% of peak FLOPs/s on A100. The N x N attention matrix is materialized in HBM (2 TB/s) when SRAM offers 19 TB/s."

Chinchilla: "Kaplan's scaling laws predict allocating most compute to model size, but our fresh fits suggest data should scale equally."

DeepSeek-V2: "MHA stores 32,768 dims per token in KV cache. Cross-head redundancy analysis shows information content fits in ~576 dims."
2
Form Hypothesis
Bottleneck + proposed modification + falsifiable prediction = hypothesis.
Template:
(1) "The current approach to [X] wastes [resource] because [mechanism]."
(2) "Replacing [X] with [Y] should reduce [resource] because [reasoning]."
(3) "At [scale], this should improve [metric] by ~[amount] with [tradeoff] as cost."
MLA hypothesis: "MHA stores redundant KV heads. Compressing to low-rank latent (d_c=512) should reduce cache 93% while preserving quality, because the bottleneck regularizes representations."
Sanity check: Does this violate any known theoretical constraint? Is the predicted effect size plausible? Would a domain expert find the reasoning convincing?
3
Small-Scale Ablation
1B parameters, 10-50B tokens, 3 seeds. One variable changed vs baseline. Explicit matching criterion.
Matching criteria (choose one, report it):
- FLOPs-matched: same total training FLOPs
- Parameter-matched: same parameter count
- Wall-clock-matched: same training time on same hardware

OLMo 2 example: Each architectural choice (RMSNorm, RoPE, QK-norm, Z-loss) tested independently against OLMo 1 baseline with same training tokens and model size. Cumulative ablations reveal interaction effects.
Minimum viable ablation table:
| Config | Change | Loss | vs Baseline |
| A (baseline) | None | 2.847 | -- |
| B | +RMSNorm | 2.831 | -0.016 |
| C | +RoPE | 2.819 | -0.028 |
| D | +QK-norm | 2.845 | -0.002 |
(Each row differs from A in exactly one way)
Evaluate Small-Scale Results
Negative: revise or abandon
Ambiguous: more seeds / larger scale
Positive: proceed to scaling
4
Scaling Plot
3-5 model sizes on log-log axes. Fit power laws. Check if curves diverge, converge, or cross.
Procedure:
1. Train baseline and variant at 125M, 350M, 760M, 1.3B, 2.7B
2. Plot validation loss (log) vs FLOPs or parameters (log)
3. Fit L(C) = alpha * C^(-beta) + L_inf to each curve
4. Extrapolate to target scale (e.g., 70B)

Interpretation:
- Persistent gap: Strong evidence for large scale (Chinchilla pattern)
- Converging: Modification may not matter at target size
- Crossing: Informative but dangerous - verify the crossing point is real
- Diverging: Modification becomes MORE valuable at scale (MLA pattern)
Chinchilla: Three independent methodologies (IsoFLOP profiles, IsoLoss contours, parametric loss fitting) all predicted the same optimal ratio. This cross-validation is the gold standard.
5
Full-Scale Validation
Run at target scale. Evaluate on diverse benchmark suite. Compare to named baselines.
Requirements:
- Diverse evaluation: knowledge, reasoning, code, math, instruction-following
- Named baselines: compare to specific published models, not "prior work"
- Multiple axes: quality, speed, memory, implementation complexity
- Error bars where feasible (multiple seeds at this scale are expensive)

Watch for:
- Benchmark overfitting (helps MMLU, hurts generation)
- Proxy-task failures (4K training says nothing about 128K behavior)
- Implementation confounds (speedup from kernels, not architecture)
OLMo 2: OLMES framework with 20 benchmarks across knowledge recall, commonsense, general reasoning, and math. All artifacts released for independent verification.
6
Analysis & Interpretation
Explain WHY it works, not just THAT it works. Identify limitations and failure modes.
Go beyond numbers:
- Flash Attention: IO complexity analysis proving O(N^2 d^2/M) HBM accesses
- Chinchilla: explaining why Kaplan's exponents were wrong (suboptimal LRs per scale)
- DeepSeek-V2: low-rank bottleneck as regularizer hypothesis

Mandatory limitations section:
(1) Where does the modification NOT help?
(2) What does it cost (complexity, kernels, training overhead)?
(3) What assumptions must hold for the claims to be valid?
7
Write Up & Release
Motivation with numbers. Method reproducible from text alone. Explicit baselines. Limitations. Code release.
Paper structure:
1. Motivation (quantified bottleneck, 1-2 paragraphs)
2. Method (equations, pseudocode, figures - implementable from paper alone)
3. Experimental setup (everything needed to reproduce)
4. Results (ablation tables, scaling plots, diverse benchmarks)
5. Analysis (why it works, not just that it works)
6. Limitations (where it fails, what it costs, what assumptions hold)

Honesty signals: negative results reported, multiple evaluation axes, current baselines (not strawmen), error bars, code release.
DeepSeek-V3: Reports $5.6M total training cost prominently. Each component (MLA, aux-loss-free balancing, MTP) gets independent ablation. Compares to specific named models. Acknowledges custom kernel requirement.
How to use this diagram: This represents the idealized linear flow. In practice, the workflow is iterative: negative results at Phase 3 loop back to Phase 2 (revise hypothesis); ambiguous results may require more data or seeds; full-scale validation may reveal issues that require new small-scale ablations. The key discipline is spending more time on Phases 1-2 (observation and hypothesis) than on Phases 3-5 (running experiments). GPU time is expensive; thinking time is free.
