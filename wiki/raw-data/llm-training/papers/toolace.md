# ToolACE: Winning the Points of LLM Function Calling
- **Core Insight:** A synthesis pipeline of three modules — Tool Self-Evolution Synthesis (26,507 APIs over 390 domains), self-guided multi-agent dialog generation, and dual-layer rule+model verification — produced LoRA-SFT data that lifted LLaMA-3.1-8B-Instruct to 59.22 overall on the BFCL-v3 leaderboard of 2024-09-20, rank 3 behind GPT-4-turbo-2024-04-09 (59.49) and GPT-4o-2024-08-06 (59.29) (§3.2, Table 2).
- **Guideline:** When synthesizing function-calling SFT data, use the model being fine-tuned as its own complexity evaluator, because using it rather than a same-size external model (Qwen1.5-7B-Chat) or a larger one (Qwen1.5-14B-Chat) gave 59.22 BFCL overall vs 57.61 and 57.67 (App. E.3, Table 8).
- **Authors:** Weiwen Liu, Xu Huang, Xingshan Zeng, Xinlong Hao, Shuai Yu, Dexun Li, et al. (Shanghai Jiao Tong University, Huawei Noah's Ark Lab, USTC, Huawei Technologies, Tsinghua University, CUHK)
- **Year:** 2024 (arXiv v1 2024-09; ICLR 2025; card checked against arXiv v2, 2025-07)
- **URL:** https://arxiv.org/abs/2409.00920
- **Source type:** paper
- **Relevant topics:** function calling, synthetic data, multi-agent dialog synthesis, data complexity control, verification, BFCL

## Abstract
ToolACE is an automatic agentic pipeline for generating accurate, complex, and diverse tool-learning data. A self-evolution synthesis process curates an API pool of 26,507 APIs. Dialogs are generated by the interplay of a user agent, an assistant agent, and a tool agent, guided by a complexity evaluator that is the LLM being trained. A dual-layer verification system combines rule-based and model-based checks. Models trained on the resulting data at 8B parameters reach performance comparable to the GPT-4 models of the time. The model and a data subset are released at https://huggingface.co/Team-ACE.

## Key Contributions
- Tool Self-Evolution Synthesis (TSS): a speciation → adaptation → evolution loop that builds a hierarchical API context tree from pretraining documents and grows API definitions from it (§2.1).
- Self-guided dialog generation (SDG): the LLM to be tuned scores sample complexity by its own token-level loss, and the user agent is instructed to complicate or simplify accordingly (§2.2).
- Dual-layer verification (DLV): a rule checker (API definition clarity, executability, dialog correctness, sample consistency) plus a model checker decomposed into hallucination detection, consistency validation, and tool-response check (§2.3).
- ToolACE-8B, a LoRA fine-tune of LLaMA-3.1-8B-Instruct, plus ablations isolating accuracy, complexity, and diversity (§3.3).

## Technical Details
- API pool: 26,507 APIs across 390 domains, against ToolLLM 16,464 APIs / 49 domains and xLAM 3,673 / 21 (Table 1). ToolACE is the only entry in Table 1 marked as covering nested parameters, parallel calls, dependent calls, and multi-type data together.
- TSS starts from API-related raw documents in pretraining data (technical manuals, API documentation, product specifications, user guides, tutorials); an agent extracts a domain and its functionalities, and children nodes are generated recursively into an API context tree (§2.1).
- Dialog types generated are four: single function calls, parallel function calls, dependent function calls, and non-tool-use dialogs (§2.2.1). Three agents role-play: user, assistant, tool. Each assistant action is generated multiple times and only responses consistent across instances are kept (§2.2.1).
- Complexity is the mean per-token negative log-likelihood of the response under the model being tuned, H_M(x,y) = −(1/n_y) Σ_i log p(t_i | x, t_1..t_{i−1}), where x is the query, y = [t_1..t_{n_y}] the response, and n_y its token count (§2.2.2, Eq. 1). It correlates positively with the number of candidate APIs, the number of APIs used, and query-API dissimilarity (§2.2.2, Figure 2).
- The complexity range is bounded by a small prior dataset: a sample the model already generates correctly gives a lower bound, a sample whose loss stays high after fine-tuning gives an upper bound (§2.2.2).
- Rule verification checks function-call executability without running the call: API name matches the tool list, all required parameters present, parameter formats matched by regular expressions (§2.3).
- BFCL-v3 results for ToolACE-8B (Table 2): overall 59.22, Non-live AST 89.27, Non-live Exec 90.07, Live AST 73.21, Multi-turn 14.37, Relevance 85.37, Irrelevance 83.81. The comparable-size fine-tuned baseline xLAM-7b-fc-r scores 51.45 overall with 0.00 multi-turn.
- API-Bank (Table 3): ToolACE-8B 75.94 Call / 47.41 Retrieval+Call, matching gpt-4-0613 on Call (75.94) and above all listed open-source models; base LLaMA-3.1-8B-Instruct is 71.18 / 37.04.
- Verification ablation (§3.3.1, Figure 3), three settings w.o. dual → w.o. model → Final: Overall 89.59 → 90.47 → 91.41 and Irrelevance 82.92 → 89.17 → 90.00. The AST and Exec bars lie in the 90.56-92.79 band; the plot does not print a legible per-bar mapping for those two groups. These post-Table-2 studies use only the non-live BFCL categories (footnote 3), so 91.41 is a non-live score, not the leaderboard overall.
- Complexity ablation (§3.3.2, Figure 4): bottom / middle / top 60,000 instances by Eq. 1 give three subsets; the medium subset is slightly best on both overall and tool-use accuracy.
- Diversity ablation (§3.3.3, Figure 5): APIs clustered into 30 groups, subsets drawn from 6 / 14 / 30 clusters with ~30,000 instances each; overall accuracy rises with diversity, with the largest gain in relevance detection.
- Data-source comparison at a fixed 25,000 samples (App. E.1, Table 6): ToolACE 58.19 overall vs xLAM 40.51 vs ToolLLM 24.90 on BFCL.
- Data-type ablation at a fixed 25,000 samples (App. E.2, Table 7): removing parallel data drops overall to 50.60; removing multi-type data drops irrelevance detection to 6.99 and overall to 42.71; removing dependent or nested data costs under 1.3 points overall.
- Model-size scaling on the Qwen-1.5-Chat series at 0.5B, 1.8B, 4B, 7B (§3.4, Figure 6): raw 0.5B and 1.8B models score 0.00 AST and 0.00 Exec and the paper states they struggle to produce structured output; fine-tuning raises every size, and fine-tuned accuracy increases monotonically with size across AST, Exec, and overall panels.
- In-context learning versus fine-tuning (App. E, Table 9): LLaMA-8B 3-shot gets 58.81 Non-live AST and 23.66 irrelevance; ToolACE fine-tuning gets 89.27 and 83.81.

## Findings relevant to generality and agentic training
- General capability after tool-data training (§3.6, Figure 8): ToolACE-8B is compared with raw LLaMA-3-8B-Instruct, raw LLaMA-3.1-8B-Instruct, xLAM-7B-fc-r, and GPT-4 on MMLU, HumanEval, GSM8K, CommonSenseQA, and BFCL. The paper reports substantial gains over xLAM-7B-fc-r, largest on MMLU, GSM8K, and CommonSenseQA, and "negligible performance degradation" versus the raw LLaMA-3.1-8B-Instruct on some benchmarks while function calling improves. Figure 8 is a radar plot; per-benchmark numbers are not printed.
- Compared with GPT-4 the paper states clear limitations in reasoning and understanding and attributes them to model and corpus scale (§3.6, App. H).
- Zero-shot API generalization is the stated motivation for API diversity, and the diversity ablation is the evidence offered: more API clusters in training raise BFCL overall accuracy and especially relevance detection (§3.3.3).
- Negative-style data: non-tool-use dialogs are generated as one of the four types and act as targets for refusing to call a tool. Removing this "Multi-type" category collapses irrelevance detection to 6.99 (App. E.2, Table 7). This is negative-as-content, not a negative gradient term.
- Stated limitations (App. H): complexity evaluation cost scales with the size of the model being trained; non-uniform sampling may bias the model toward samples it already handles; general capability still trails GPT-4.
