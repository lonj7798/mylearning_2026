# TTSService — the text-to-audio boundary and what actually crosses it

<!-- slug: tts-service-interface · type: source · source: src/pipecat/services/tts_service.py -->

**Core Insight.** Pipecat's TTS layer is not "text in, audio out" — it is a *reordering buffer*. `TTSService` owns sentence aggregation, a per-turn "audio context" FIFO, and word-timestamp bookkeeping, and the single thing it optimises for is the interval between a text arriving and the first *audible* PCM sample leaving. Everything after that first sample is hidden behind real-time playback, so the whole design (chunking, context serialization, TOKEN mode, TTFA metric) exists to shrink one number.

**Guideline.** Pick your aggregation mode deliberately: `TextAggregationMode.SENTENCE` (the default) will not call `run_tts` until a sentence boundary is confirmed *and* a non-whitespace lookahead character has arrived — its own docstring budgets "~200-300ms per sentence". Use `TOKEN` only with a provider whose prosody survives token-sized inputs. And instrument `TTFAMetricsData`, not `TTFBMetricsData`: the difference between them is `leading_silence`, which is invisible to byte-level monitoring and fully audible to the user.

## Technical Details

- **Base class**: `class TTSService(AIService)` — `tts_service.py:109`, `__init__` at `:145`, 2136 lines total. Single abstract method:
  `async def run_tts(self, text: str, context_id: str) -> AsyncGenerator[Frame | None, None]` (`:539`). Yielding `None` is the websocket contract — "audio arrives on my receive loop, I own context lifetime" (`tts_process_generator`, `:1347`).
- **Subclass ladder is thinner than it looks.** Real: `TTSService` → `WebsocketTTSService(TTSService, WebsocketService)` (`:1899`) → `InterruptibleTTSService(WebsocketTTSService)` (`:1969`, reconnects the socket on barge-in when `_bot_speaking or _tts_started`). **Everything with "Word" in the name is deprecated**: `WordTTSService` (`:1882`), `WebsocketWordTTSService` (`:2040`), `InterruptibleWordTTSService` (`:2062`), `AudioContextTTSService` (`:2083`), `AudioContextWordTTSService` (`:2121`) — all `.. deprecated:: 0.0.105`, removal 2.0.0, because "Word timestamp functionality is now always active in TTSService."
- **HTTP vs streaming is a flag, not a class.** `supports_processing_metrics` (`:423`) returns `True` on `TTSService`, `False` on `WebsocketTTSService` (`:1926`) — "run_tts sends the text and returns, and audio arrives later on the receive task." Chunked-HTTP services buffer via `chunk_size` (`:474`): `CHUNK_SECONDS = 0.5; return int(self.sample_rate * CHUNK_SECONDS * 2)` — download 0.5 s before pushing the first frame so playback doesn't glitch.
- **How text arrives.** LLM emits `LLMTextFrame` (`frames.py:343`). Either an upstream `LLMTextProcessor` (`processors/aggregators/llm_text_processor.py:30`) converts it to `AggregatedTextFrame` via `BaseTextAggregator.aggregate()` (`:84`), or `TTSService` does it internally with its own `SimpleTextAggregator(aggregation_type=...)` (`tts_service.py:328`). `TextAggregationMode` (`:82`) is `SENTENCE` | `TOKEN`.
- **`SentenceAggregator` is a decoy.** `processors/aggregators/sentence.py:18` is a 63-line standalone `FrameProcessor` that buffers `TextFrame` until `match_endofsentence()` and pushes one `TextFrame`. It is **not** in the TTS path — TTSService never touches it. Don't confuse the two.
- **Boundary detection**: `match_endofsentence()` (`utils/string.py:151`) = NLTK + punctuation check. `SENTENCE_ENDING_PUNCTUATION` (`:73`) includes `。？！；．｡` and Indic/Arabic marks; `UNAMBIGUOUS_SENTENCE_ENDING_PUNCTUATION` (`:125`) is the non-Latin subset used "as a fallback when NLTK doesn't support the language (e.g., Japanese, Chinese, **Korean**, Hindi, Arabic)". `SimpleTextAggregator._check_sentence_with_lookahead` defers the NLTK call until the first non-whitespace char *after* the punctuation, to tell `"$29."` from `"$29. Next"` — one extra token of latency per sentence, by design.
- **Audio out**: `TTSAudioRawFrame(OutputAudioRawFrame)` (`frames.py:241`) carrying `context_id: str | None`. Built in `_stream_audio_frames_from_iterator()` (`tts_service.py:968`) — strips WAV headers, resamples, 2-byte-aligns. Bracketed by `TTSStartedFrame` (`frames.py:2210`: `context_id`, `append_to_context`) and `TTSStoppedFrame` (`:2231`: `context_id`).
- **Word/boundary frames — what really exists.** Grepping `frames.py` for `word|boundary|timestamp` returns **no dedicated word-boundary or timestamp frame class**. There is no `WordBoundaryFrame`, no `TTSWordFrame`. Word-level information is carried by exactly two things:
  1. `TTSTextFrame(AggregatedTextFrame)` (`frames.py:417`) with its `pts` (nanoseconds) stamped by the sequencer — one frame per word token, emitted *as the word is spoken*.
  2. `AggregatedTextProgressFrame(DataFrame)` (`frames.py:424`) — `segment_id, context_id, text, aggregated_by, accumulated_text, remaining_text`, "emitted alongside each TTSTextFrame during word-timestamp playback" for word-level highlighting.
  The internal `@dataclass _WordTimestampEntry` (`tts_service.py:100`) never leaves the service; it is queued into the audio context so timestamps interleave with audio in strict playback order.
- **Word-timestamp API** (what a provider subclass calls): `start_word_timestamps()` (`:1380`, sets the PTS baseline), `reset_word_timestamps()` (`:1399`), and
  `add_word_timestamps(word_times: list[tuple[str, float]], context_id=None, includes_inter_frame_spaces=None, pre_merge_tokens=False)` (`:1406`). `pre_merge_tokens=True` runs `merge_punct_tokens` for providers that emit spaces/punctuation as separate tokens (Inworld).
- **Where TTFA is measured** — `_handle_audio_context` (`:1710`), on the first `TTSAudioRawFrame` of a context:
  `await self.stop_ttfb_metrics()` → `await self.start_word_timestamps()` (`:1738-1740`), then `await self.process_ttfa_metrics(frame)` on *every* audio frame (`:1741`). `TTFAMetricsData` (`metrics/metrics.py:41`) reports `ttfa`, `ttfb`, and `leading_silence`, where **`ttfa = ttfb + leading_silence`** and TTFA runs to the "first audible sample". A provider that pads 150 ms of silence looks perfect on TTFB and sounds slow.
- **Why time-to-first-audio dominates perceived latency.** The voice loop is serial up to the first sample and parallel after it. Audio plays at 1× wall clock, so every byte synthesised after the first chunk is produced *underneath* playback and costs the listener nothing. Only the gap `[LLM decided → first audible sample]` is exposed, and it is the sum of three things the TTS layer controls: (a) aggregation delay — SENTENCE mode waits for a full sentence plus a lookahead char before `run_tts` is even called; (b) provider TTFB; (c) `leading_silence`. Total synthesis throughput is essentially irrelevant unless it falls below real time. This is why the codebase spends its complexity budget on the `_serialization_queue: FrameQueue` (`:405`) and per-context ordering rather than on synthesis speed.
- **Ordering is explicit, not incidental.** A single `_serialization_queue: FrameQueue` (`:405`) holds three item kinds — a `str` context ID (drain that context's audio queue in full), a `Frame` (emit in order relative to surrounding contexts), and `None` (shutdown sentinel from `stop()`). Per-turn contexts come from `create_context_id()` (`:526`), which reuses `_turn_context_id` when `reuse_context_id_within_turn=True` so every sentence of one LLM turn shares one audio context. Two cursors are kept deliberately separate (`:375-391`): `_turn_context_id` clears when synthesis ends, `_playing_context_id` clears when playback ends.
- **`TTSSpeakFrame`** (`frames.py:795`) is the out-of-band path — `process_frame` (`:842`) temporarily nulls `_turn_context_id` so the utterance gets a fresh UUID context and does not join the LLM turn.
- **Interruption**: `_handle_interruption` (`:1030`) clears `_processing_text`, `_bot_speaking`, `_streamed_text`, resets the text aggregator and every `BaseTextFilter`. `InterruptibleTTSService` additionally tears down and reopens the websocket (`:1992-2002`) because a half-spoken server-side context cannot be rewound. Uninterruptible frames survive the queue `reset()` (`:402-404`).
- **Silent-failure guard**: `max_consecutive_zero_audio_contexts: int = 3` (`:168`) — a provider that accepts every request and returns no audio (unknown voice ID) surfaces no error, so after 3 silent contexts the service reports a permanent error and stops being given work.
- **Two knobs that trade latency for smoothness**: `pause_frame_processing` (`:164`) halts inbound frame processing while audio is still to be played, so a fast LLM cannot overlap the previous turn's audio; `push_silence_after_stop` / `silence_time_s: float = 2.0` (`:160-162`) appends trailing silence after `TTSStoppedFrame`. Both add tail latency, neither touches TTFA.
- **Migration angle:** boson-agent has **no TTS today** — `packages/gateway/gateway/` is text-only over websocket, so `TTSService` replaces nothing and is purely additive. It *collides* with `gateway/server/websocket.py` (734 L), which today streams assistant text tokens straight to the client: under Pipecat that token stream becomes the input to `LLMTextProcessor`/`TTSService`, and the authoritative "what was actually said" record moves from `gateway/server/history.py` (70 L) to Pipecat's `TTSTextFrame.append_to_context` path. It *partly collides* with `gateway/interrupt/cancellation.py` (`CancellationFlag`, 187 L, cooperative flag checked between agent-loop iterations): Pipecat's `InterruptionFrame` + `_handle_interruption` + audio-context wipe covers the same job but adds something boson cannot do — truncating the assistant context at the **last spoken word** via `TTSTextFrame` PTS, rather than at the last generated token. `gateway/interrupt/fillers.py` (40 L) is *user-side* filler suppression (`is_filler(text, agent_status)`) and is orthogonal — it survives the migration untouched.
