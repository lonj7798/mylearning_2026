# Pipecat Flows — the state machine that ships in the box

<!-- slug: flows-state-machine · type: module · source: src/pipecat/flows/manager.py (898 L), src/pipecat/flows/__init__.py (73 L), src/pipecat/flows/actions.py (400 L) -->

**Core Insight.** Pipecat *does* ship a conversation state machine — `pipecat.flows.FlowManager`, 898 lines in `manager.py` — and it is **not a `FrameProcessor`**. It is a plain object that sits *beside* the pipeline holding a `PipelineWorker` reference and drives the LLM from outside by queueing frames into the head of the pipeline (`await self._worker.queue_frames([...])`, manager.py:841). A "state" is not a registered object: it is a `NodeConfig` dict handed to `_set_node()`, and entering it always rewrites the LLM's messages **and** its entire advertised tool array. Transitions fire from **two** independent paths — an LLM function call returning `(result, next_node)`, or plain code calling the public `await flow_manager.set_node_from_config(node)` — so Flows does *not* force transitions through the model.

**Guideline.** Treat Flows as a *context-and-tools rewriter with a node label attached*, not as a graph engine. It gives you the hard part (atomic swap of system instruction + messages + tools + inference trigger, correctly sequenced against in-flight function calls). It gives you **nothing** for transition legality, node registration, or graph introspection — `_set_node` accepts any config from anywhere with no from→to check. Keep your own guard layer.

## Technical Details

- **Construction is keyword-only** (manager.py:91-101). `FlowManager(*, llm: LLMService | LLMSwitcher, context_aggregator: Any, worker: PipelineWorker | None = None, task: PipelineWorker | None = None, context_strategy: ContextStrategyConfig | None = None, transport: BaseTransport | None = None, global_functions: list[FlowsFunctionSchema | FlowsDirectFunction] | None = None)`. `task` is deprecated since 1.5.0 → use `worker`; passing both raises `ValueError` (L121-132). Default strategy when unset: `ContextStrategyConfig(strategy=ContextStrategy.APPEND)` (L141-143).
- **It is not in the pipeline.** In `examples/flows/hello_world.py:135-167` the `Pipeline([...])` list contains transport / stt / aggregators / llm / tts — **no flow object**. `PipelineWorker(pipeline, ...)` is built, `runner.add_workers(worker)`, and only then `FlowManager(worker=worker, llm=llm, context_aggregator=context_aggregator, transport=transport)`. The flow is kicked off from a transport event: `@transport.event_handler("on_client_connected")` → `await flow_manager.initialize(create_initial_node())` (L169-173).
- **Two pipeline touch points, both via the worker, never via subclassing.** (1) frames out: `queue_frames`/`queue_frame`. (2) frames in: `ActionManager.__init__` calls `worker.set_reached_downstream_filter((ActionFinishedFrame, FunctionActionFrame, BotStoppedSpeakingFrame))` and registers `@worker.event_handler("on_frame_reached_downstream")` (actions.py:109-127) so deferred post-actions run on `BotStoppedSpeakingFrame`.
- **Public API surface is small.** `async initialize(initial_node: NodeConfig | None = None) -> None` (L292); `async set_node_from_config(node_config: NodeConfig) -> None` (L588); `get_current_context() -> list[dict]` (L336, reads `self._context_aggregator.user()._context`); `register_action(action_type: str, handler: Callable) -> None` (L353); properties `state -> dict[str, Any]` (L157), `transport` (L188), `current_node -> str | None` (L219), `worker -> PipelineWorker` (L251), deprecated `task` (L280).
- **`_set_node(node_id, node_config)` is the whole machine** (L602-723). Its own docstring lists the order: (1) pre-actions, (2) role + task messages, (3) register node functions, (4) update LLM context with messages and tools, (5) update state, (6) trigger completion, (7) post-actions. Concretely it: clears `self._pending_transition`; `_validate_node_config`; `self._action_manager.clear_deferred_post_actions()`; registers handlers found in `pre_actions`/`post_actions` configs; runs pre-actions; builds `functions_list = self._global_functions + node_config.get("functions", [])`; wraps each into a `FunctionSchema` carrying a handler; sets `self._current_node = node_id`; and queues frames. Raises `FlowTransitionError` if `not self._initialized`, wraps anything else in `FlowError(f"Failed to set node {node_id}: ...")`.
- **What a node transition actually emits** (`_update_llm_context`, L734-849) — an ordered frame batch through `queue_frames`:
  1. `LLMUpdateSettingsFrame(delta=LLMSettings(system_instruction=role_message))` — only if `role_message` is set; it persists across nodes until another node sets it.
  2. `LLMMessagesAppendFrame(messages=messages)` **or** `LLMMessagesUpdateFrame(messages=messages)` — the choice *is* the ContextStrategy: `frame_type = LLMMessagesUpdateFrame if update_config.strategy in [ContextStrategy.RESET, ContextStrategy.RESET_WITH_SUMMARY] else LLMMessagesAppendFrame` (L831-836).
  3. `LLMSetToolsFrame(tools=functions)` — **unconditional** (L839). If the node declares no functions, `formatted_tools` is `NOT_GIVEN` (L670-672) and the node *clears* the tool set.
  4. `LLMRunFrame()` — queued separately at L709, only `if node_config.get("respond_immediately", True)`.
- **Tool handlers ride inside the schema.** `_create_function_schema` (L552-586) returns `FunctionSchema(name, description, properties, required, handler=transition_func)` where `transition_func = tool_options(cancel_on_interruption=tool.cancel_on_interruption, timeout_secs=tool.timeout_secs)(await self._create_transition_func(tool.name, handler))`. The LLM service auto-registers advertised handlers on the context frame (`_sync_registered_tool_handlers(frame.context.tools)`, `services/llm_service.py:723`) — Flows never calls `register_function`.
- **Transition path A — LLM function call.** `_create_transition_func(name, handler)` (L443) returns an inner `async def transition_func(params: FunctionCallParams) -> None`. It invokes the handler, then: if the response is a tuple it unpacks `result, next_node`; a `None` result is replaced by `{"status": "acknowledged"}` (transition-only function, L480-482). Then the branch that matters (L496-514):
  ```python
  is_no_response = next_node is NO_RESPONSE
  if is_no_response or not next_node:                       # node function: stay put
      properties = FunctionCallResultProperties(run_llm=not is_no_response, on_context_updated=None)
  else:                                                     # edge function: transition
      self._pending_transition = {"next_node": next_node, "function_name": name,
                                  "arguments": params.arguments, "result": result}
      properties = FunctionCallResultProperties(run_llm=False,
                                                on_context_updated=self._check_and_execute_transition)
  await params.result_callback(result, properties=properties)
  ```
  `_check_and_execute_transition` (L525) is the concurrency guard: it fires only when `not assistant_aggregator.has_function_calls_in_progress`, so a parallel tool batch cannot transition mid-batch. Errors inside the handler never crash the turn — they become `{"status": "error", "error": str(e)}` (L518-521).
- **Transition path B — code, no LLM involved.** `set_node_from_config` is public and callable from any coroutine. Proven twice in-tree: `examples/flows/warm_transfer.py:658` transitions from a Daily transport callback guarded on flow state — `if user_id == "agent" and flow_manager.current_node == "transferring_to_human_agent": await start_human_agent_interaction(flow_manager=flow_manager)` (which calls `set_node_from_config`, L259-261); and `examples/flows/multi_worker_handoff.py:352` re-seeds a node from `@worker.event_handler("on_activated")`.
- **Static vs dynamic flows do not exist at this commit — expectation violated.** `grep -rn "FlowConfig"`, `grep -rni "static flow\|static_flow"`, and `grep -rni "dynamic flow\|dynamic_flow"` over the whole repo return **zero hits**. There is no `FlowConfig`, no JSON flow document, no declarative edge table, and `__init__.py`'s `__all__` (L48-73) does not export one. Only the runtime-determined style survives: nodes are Python functions returning `NodeConfig`, edges are the second tuple element a handler returns. The package docstring says it plainly: "Pipecat Flows determines conversation structure at runtime" (`__init__.py:12-13`).
- **No transition validation, and no node registry.** `_validate_node_config` (L867-898) checks exactly two things: `"task_messages" not in config` → `FlowError`, and each entry of `functions` is callable or a `FlowsFunctionSchema` → else `InvalidFunctionError`. There is **no** legality check of current→target. Node identity is `get_or_generate_node_name(node_config)` = `node_config.get("name", str(uuid.uuid4()))`, so an unnamed node gets a throwaway UUID. `self._current_functions: set[str]` (L148) is assigned at L704 and **never read anywhere in the codebase** — it is dead state, not a gate.
- **Actions are the side-effect channel.** Built-ins registered in `ActionManager.__init__`: `tts_say` → `TTSSpeakFrame(text, append_to_context=...)`, `end_conversation` → optional `TTSSpeakFrame` then `EndFrame()`, `function` → `FunctionActionFrame(action, function)` executed when it reaches the pipeline tail. `_maybe_wait_for_ongoing_actions_to_finish` (L249-300) encodes the ordering rule: after a `tts_say`, wait unless the next action is `tts_say`/`end_conversation`/`function`; after a `function`, always wait.
- **`LLMAdapter` (adapters.py, 68 L) is not a provider adapter** — it only does summaries: `format_summary_message(summary) -> dict` returning a `{"role": "developer", ...}` message, and `generate_summary(llm, summary_prompt, context)` which builds a throwaway `LLMContext` and calls `llm.run_inference(summary_context, system_instruction=summary_prompt)` out of band. `manager.py:801-807` wraps it in `asyncio.wait_for(..., timeout=5.0)` and silently falls back to `APPEND` on failure or timeout.
- **Exceptions** (exceptions.py, 62 L): `FlowError` ← `FlowInitializationError`, `FlowTransitionError`, `InvalidFunctionError`, `ActionError`.
- **Migration angle:** this reverses the course's working assumption. boson's `StageMachine` (`gateway/stage/machine.py`, 101 L) does **not** have to survive as a hand-written `FrameProcessor` — `FlowManager` is a real counterpart. Map it as: `StageDefinition{name, prompt, tools, skills, transitions}` → `NodeConfig{name, task_messages/role_message, functions}`; `build_stage_injection(stage)` → the node's `task_messages` developer message; `StageContext.filter_tools(all_tools)` → the node's `functions` list, since `_set_node` re-emits `LLMSetToolsFrame` on every transition (this **collides** with boson's `_allowed_tools_var` ContextVar gate in `metatool/router.py` — pick one). And crucially boson's transition trigger survives: `RuleEngine.evaluate(...)` → `Action` → `ExecutionResult.pending_transition` → `core._apply_stage_transition(session, target)` becomes a rule processor holding a `flow_manager` reference and calling `await flow_manager.set_node_from_config(node_for(target))`. **Four real frictions, none fatal.** (1) *Legality is lost*: `StageMachine.transition(from_stage, to_stage)` returning `TransitionResult(success=False, error="Transition 'a' -> 'b' not allowed")` has no Flows counterpart — keep `StageMachine` as a pure validator in front of `set_node_from_config` and throw away only its prompt/tool plumbing. (2) *Every transition is an inference trigger by default*: `respond_immediately` defaults `True`, so a rule-driven transition fired on the user's turn queues `LLMRunFrame()` and speaks immediately; boson's transition is silent bookkeeping before the loop runs, so ported nodes need `respond_immediately=False`. (3) *There is no silent transition*: `LLMSetToolsFrame` is always emitted, and `task_messages` is a required key — the closest thing to a no-op node is `task_messages=[]`, which passes validation because `_validate_node_config` only checks key presence. (4) *Ordering becomes queue ordering*: boson calls `_apply_stage_transition` inline before `run_agent_loop`; Flows pushes frames from the **head** of the pipeline via `queue_frames`, so an in-pipeline rule processor and the flow's own frames race through the same queue rather than executing in call order. **Untouched:** boson's `<system-reminder>` protocol, `ContextManager.pop_pending_reminders()`, and the per-stage skill list (`StageDefinition.skills`) have no Flows concept at all.
