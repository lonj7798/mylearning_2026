# boson-agent's Tool + Metatool Subsystem — `@tool`, ToolRouter, `use_tool` / `use_skill`

<!-- slug: boson-tool-router · type: boson · source: packages/basement/basement/tools/{decorator,registry,executor}.py, packages/basement/basement/metatool/{router,tools,registry}.py, packages/basement/basement/skills/injector.py, packages/basement/basement/llm/ -->

**Core Insight.** boson hides its tools from the model on purpose. When `enable_tool_router` is on, the LLM is shown only the meta-tools `use_tool` / `use_skill`, and every real tool is reached indirectly as `use_tool(tool_name="…", arguments={…})` through a `ToolRouter` dispatch table that unifies native `@tool` functions and MCP tools behind one name space. Tool *exposure* (what the model sees) and tool *permission* (what may run) are therefore two separate gates, and per-stage access control is a third — a ContextVar allowlist checked inside `dispatch`.

**Guideline.** Keep the three gates distinct when porting: advertise a small stable tool array (cache-friendly), enforce availability at dispatch time, and enforce permission independently. Do not collapse "the model can see it" into "the model may call it" — boson deliberately keeps the advertised array byte-stable across stages to preserve prompt caching while the allowlist changes underneath.

## Technical Details

- **`@tool` decorator** (`tools/decorator.py:26`): `def tool(fn: Callable | None = None, *, name: str | None = None) -> Callable`. It **requires a docstring** — `raise ValueError(f"Tool '{func.__name__}' must have a docstring (used as description)")` (L42-45). It builds `ToolSpec(name=name or func.__name__, description=func.__doc__.strip(), input_schema=_generate_schema(func), handler=func)`, stashes it as `func.__tool_spec__`, and returns the function **unchanged**. `_generate_schema` (L61) walks `inspect.signature`, maps types via `TYPE_MAP = {str:"string", int:"integer", float:"number", bool:"boolean"}` (L18-23), handles `list[X]` and `Optional[X]`, defaults unannotated params to `{"type":"string"}`, and marks a param `required` iff `param.default is inspect.Parameter.empty`. Real example (`agents/demo/tools/weather.py`):
  ```python
  @tool
  def get_weather(city: str) -> str:
      """Get the current weather for a city. Returns temperature and conditions."""
  ```
- **`ToolSpec`** (`schemas/tool_schema.py:15`) is a pydantic model of exactly four fields: `name: str`, `description: str`, `input_schema: dict`, `handler: Callable = Field(exclude=True)`.
- **Registration is filesystem discovery.** `ToolRegistry.discover_tools(tools_dir: Path) -> int` (`tools/registry.py:54`) globs `*.py` (skipping `_`-prefixed), imports each via `_import_module_from_path` (a `importlib.util.spec_from_file_location` with a sha1-suffixed module name, L24-45), and registers any object with `__tool_spec__` **whose `__module__` matches** so re-exported siblings are not double-registered (L72-74). `register(spec)` raises `ValueError(f"Duplicate tool name: '{spec.name}'")`. `get_all_specs() -> list[ToolSpec]` is what feeds the LLM `tools` parameter.
- **`ToolRouter`** (`metatool/router.py:37`): `__init__(self, permission_checker: PermissionChecker | None = None)`; state is `self._dispatch_table: dict[str, ToolSpec]`. `register_native(tool_registry) -> int` (L75) and `register_mcp(mcp_manager) -> int` (L87) both fill the same table, so an MCP tool and a native tool are indistinguishable downstream. `async dispatch(self, tool_name: str, arguments: dict) -> ToolResultBlock` (L103) does, in order: (1) `self._permission_checker.check_tool(tool_name)` → raises `PermissionDeniedError`; (2) stage gate — `allowed = _allowed_tools_var.get()`; if not `None` and `tool_name not in allowed and tool_name not in meta_tool_names()`, return an `is_error=True` `ToolResultBlock` with content `f"Tool '{tool_name}' is not available in the current stage."`; (3) `ToolNotFoundError` if absent; (4) `return await _invoke_handler(spec, arguments)`. `set_allowed_tools(tool_names: list[str] | None)` (L57) writes `_allowed_tools_var: ContextVar[set[str] | None]` (L32) — per-asyncio-task so one router instance serves concurrent sessions.
- **Invocation is one shared function.** `_invoke_handler(spec, arguments)` (`tools/executor.py:67`) is the canonical run+wrap for both `ToolRouter.dispatch` and `execute_tool(registry, name, tool_input)` (L121) "so the two paths cannot drift". Async handlers: `await spec.handler(**arguments)`. Sync handlers: off-loop in `asyncio.to_thread` under a module-level `threading.Lock`, shielded so cancellation cannot discard a completed side effect (see [[boson-agent-loop]]). Return-value contract: a returned `ToolResultBlock` passes through unchanged, anything else is `str()`-ified into `ToolResultBlock(tool_use_id=f"toolu_{uuid4().hex[:12]}", content=str(value), is_error=False)`; exceptions become `f"Tool error: {type(error).__name__}: {error}"` with `is_error=True`.
- **The `use_tool` meta-tool** (`metatool/tools.py:23`, `create_use_tool(router: ToolRouter) -> ToolSpec`). Advertised signature — the tool-call shape the model must emit:
  ```json
  {"type":"object",
   "properties":{"tool_name":{"type":"string","description":"Name of the tool to call"},
                 "arguments":{"type":"object","description":"Arguments to pass to the tool"}},
   "required":["tool_name","arguments"]}
  ```
  description: `"Call a tool by name. Use only tools listed in the current stage instructions."` The handler `_use_tool_handler(tool_name, arguments)` (L46) defends the one un-gated seam on the LLM path: `arguments` arriving as a **JSON string** is `json.loads`-ed back into a dict (L56-64); a non-object payload returns a clean `is_error` result rather than `**`-unpacking a non-mapping (L65-92). Then `return await router.dispatch(tool_name, arguments)`.
- **The `use_skill` meta-tool** lives in `skills/injector.py:59` — `create_use_skill(registry, api, hook_registry=None, permissions=None, *, conversation_api_resolver=None) -> ToolSpec`. Schema is `{"skill_name": {"type":"string"}}`, required. The handler checks `permissions.check_skill`, fires `ON_SKILL_INVOKE`, and returns the template **inline** as the tool result: `return f"<system-reminder>\n{skill.prompt_template}\n</system-reminder>"` (L105) — deliberately *not* the `inject_system_reminder` queue, because the per-turn `ConversationAPI` binding was stale on the PreTool path (L80-86). The queue path (`inject_skill`, L26) is slash-command only.
- **Meta-tool registry** (`metatool/registry.py`): `BUILTIN_META_TOOLS = frozenset({"use_tool", "use_skill"})`, `_EXTRA_META_TOOLS: set[str]`, plus `register_meta_tool(name)`, `meta_tool_names()`, `extra_meta_tool_names()`. **Expected-but-absent:** the docstring advertises promoting a native tool (e.g. `transition_stage`) to always-callable meta-tool, but `grep -rn "register_meta_tool"` finds **no call site anywhere in the repo** at this commit — only the definition and its own docstring. The extensibility exists; nothing uses it.
- **Wiring.** `gateway/core.py:108-119`: if `agent_config.enable_tool_router` (default `False`, `schemas/config_schema.py:67`), build `ToolRouter(permission_checker=self._permissions)`, `register_native(self._tool_registry)`, optionally `register_mcp(self._mcp_manager)`, then `self._tool_registry.register(create_use_tool(self._tool_router))` — the meta-tool is itself a normal registry entry. `use_skill` is registered once process-wide with `conversation_api_resolver=self._current_conversation_api` (L129-135) to avoid cross-session hook leakage (issue #63). Exposure is decided per stage at `core.py:280-303`; under `maximize_caching` it is pinned to `{"use_tool","use_skill"}` because "the prompt-cache prefix is ordered tools → system → messages, so changing exposure on a stage transition invalidates the entire cached conversation."
- **LLM providers supported — 6 factories in `PROVIDER_REGISTRY`** (`llm/registry.py:61-68`): `"anthropic"`, `"openai"`, `"google"`, `"boson"`, `"xai"`, `"openrouter"`. `get_provider(config)` dict-dispatches and raises `ProviderError` on an unknown name. All implement the `LLMProvider` Protocol (`llm/base.py:64`): `def stream(self, messages: list[Message], system: str, tools: list[ToolSpec] | None = None) -> AsyncIterator[StreamEvent]`. Per-provider tool shaping:
  - **Anthropic** (`anthropic_provider.py:42`): `{"name","description","input_schema"}`, `system` as a separate top-level kwarg, `extra_body={"cache_control": {"type":"ephemeral"}}` on every request (L91). Emits `ToolUseStart` from `content_block_start`, `InputJsonDelta(partial_json, tool_use_id=current_tool_id)` from `input_json_delta`.
  - **OpenAI** (`openai_provider.py:101`): `{"type":"function","function":{"name","description","parameters"}}` — note `parameters`, not `input_schema`. System prompt becomes a leading `{"role":"system"}` message (L123). Parallel `tool_calls` arrive interleaved and are keyed by index; `_MODELS_WITHOUT_CUSTOM_TEMPERATURE` (L52) suppresses `temperature` for o-series/gpt-5 builds.
  - **Google** (`google_provider.py:72`): `types.Tool(function_declarations=[types.FunctionDeclaration(name, description, parameters=params if params.get("properties") else None)])`, with `Part.from_function_call` / `function_response` pairing and an opaque `thought_signature` on Gemini 2.5.
  - **boson / xai / openrouter** are OpenAI-compatible subclasses: `BosonProvider` (vLLM endpoint, `extra_body={"chat_template_kwargs":{"enable_thinking": False}}`), `XaiProvider(OpenAIProvider)` overriding `_make_client` for `https://api.x.ai/v1` and remapping `max_completion_tokens` → `max_tokens`, `OpenRouterProvider`.
- **Migration angle:** Pipecat's adapter layer replaces `basement/llm/*` wholesale — 12 concrete adapters in `src/pipecat/adapters/` already do the per-provider tool shaping that boson hand-writes six times, and `BaseLLMAdapter.to_provider_tools_format(tools_schema)` is the exact seam of `_convert_tools`. Concretely: `@tool` → a Pipecat **direct function** (docstring already carries the description, and `DirectFunctionWrapper.to_function_schema()` does the same signature→JSON-Schema derivation `_generate_schema` does) or a `FunctionSchema(name, description, properties, required, handler=...)`; `ToolRegistry.discover_tools()` has **no Pipecat equivalent** — auto-discovery from a `tools/` directory must be kept as boson glue that produces the `tools=[…]` list handed to `LLMContext`. `ToolRouter.dispatch` collides with `LLMService.run_function_calls` / `_run_function_call`, which already re-resolves the handler, arms timeouts, and settles results — but Pipecat's registry (`self._functions: dict[str | None, FunctionCallRegistryItem]`) has **no permission check and no stage allowlist**, so `PermissionChecker.check_tool` and the `_allowed_tools_var` ContextVar gate must survive as handler-side guards or a wrapping catch-all (`register_function(None, handler)`). The `use_tool` indirection survives intact as a two-entry `LLMContext(tools=[use_tool, use_skill])` with per-stage swaps via `LLMSetToolsFrame` (and `add_tool_change_messages=True` on the aggregator pair). Two contract mismatches to plan for: (1) Pipecat handlers return results via `await params.result_callback(result)` and receive one `FunctionCallParams` object — boson handlers are `handler(**arguments)` returning a value, so every one of the 22 tools under `agents/*/tools/` needs a signature change or a shim; (2) boson runs tools **sequentially** inside `_execute_tool_uses`, Pipecat defaults `run_in_parallel=True` with a shared `group_id`, so the `_SYNC_HANDLER_LOCK` mutual-exclusion assumption (`tools/executor.py:30`, "production tools do read-modify-write on shared YAML/JSON files") must be re-asserted explicitly. `MCPManager` is left largely untouched: Pipecat has its own MCP support, but boson's `register_mcp` merely flattens specs into the same table, which maps to appending them to the `tools` list.
