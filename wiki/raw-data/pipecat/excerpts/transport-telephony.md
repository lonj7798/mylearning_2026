# Telephony in Pipecat — there is no telephony transport, only serializers

<!-- slug: transport-telephony · type: source · source: src/pipecat/serializers/{twilio,telnyx,plivo,exotel,genesys,vonage}.py + src/pipecat/runner/utils.py -->

**Core Insight.** A Pipecat phone call is **a WebSocket transport plus a provider-specific `FrameSerializer`** — nothing more. `src/pipecat/transports/` contains **no `twilio/` and no `telnyx/` directory**; the entire telephony surface is six files under `src/pipecat/serializers/`. The serializer is also where the 8 kHz μ-law reality of the PSTN enters the pipeline: it is the codec boundary, the resample point, the call-control client, and the DTMF decoder, all in one ~300-line class.

**Guideline.** Treat the serializer as the telephony adapter and budget for it accordingly: every provider you add is a new serializer, not a new transport. And design your STT/TTS choices around the fact that inbound audio was **8 kHz μ-law before you ever saw it** — upsampling to 16 kHz restores sample count, not bandwidth.

## Technical Details

**Correction to the course outline (verified).** `ls src/pipecat/transports/` at this commit returns exactly: `base_input.py`, `base_output.py`, `base_transport.py`, `daily/`, `heygen/`, `lemonslice/`, `livekit/`, `local/`, `moq/`, `smallwebrtc/`, `tavus/`, `vonage/`, `websocket/`, `whatsapp/`. No `twilio`, no `telnyx`, no `plivo`, no `sip`. `ls src/pipecat/serializers/` returns `base_serializer.py`, `exotel.py` (171 L), `genesys.py` (964 L), `plivo.py` (256 L), `protobuf.py` (165 L), `telnyx.py` (292 L), `twilio.py` (314 L), `vonage.py` (188 L). (`transports/vonage/` exists but is `VonageVideoConnectorTransport` — video, unrelated to `serializers/vonage.py`.)

The framework's own wiring proves the architecture. `src/pipecat/runner/utils.py:486` — `_create_telephony_transport(websocket, params, transport_type, call_data) -> BaseTransport` — sets `params.add_wav_header = False`, assigns `params.serializer = TwilioFrameSerializer(...)` / `TelnyxFrameSerializer(...)` / `PlivoFrameSerializer(...)` / `ExotelFrameSerializer(...)`, then returns `FastAPIWebsocketTransport(websocket=websocket, params=params)` (line 554). The `create_transport()` docstring maps keys `"twilio"`, `"telnyx"`, `"plivo"`, `"exotel"` all to `FastAPIWebsocketParams` factories. One transport, four serializers. See `[[transport-websocket]]`.

**`FrameSerializer`** (`base_serializer.py:23`) is a 106-line ABC over `BaseObject`:
`async def setup(setup: FrameProcessorSetup)`, `@abstractmethod async def serialize(frame) -> str | bytes | None`, `@abstractmethod async def deserialize(data) -> Frame | None`, plus `should_ignore_frame()`. `InputParams` carries `ignore_rtvi_messages: bool = True` and `resampler_clear_after_secs: float | None = 0.2` — the latter documented as: set to `None` "for telephony providers (e.g. Genesys) that have irregular gaps between audio chunks."

**Audio format — be concrete.**

| Serializer | Wire rate | Codec | Notes |
|---|---|---|---|
| `TwilioFrameSerializer` | `twilio_sample_rate: int = 8000` | μ-law (`pcm_to_ulaw` / `ulaw_to_pcm`) | base64 in JSON `{"event":"media","streamSid":...,"media":{"payload":...}}` |
| `TelnyxFrameSerializer` | `telnyx_sample_rate: int = 8000` | `inbound_encoding`/`outbound_encoding`, `"PCMU"` (μ-law) default, `"PCMA"` (A-law) supported; anything else `raise ValueError(f"Unsupported encoding: ...")` | |
| `PlivoFrameSerializer` | `plivo_sample_rate: int = 8000` | μ-law, `"contentType": "audio/x-mulaw"` | |
| `ExotelFrameSerializer` | `exotel_sample_rate: int = 8000` | **raw PCM**, resample only — no companding | |
| `GenesysAudioHookSerializer` | `genesys_sample_rate: int = 8000` | `AudioHookMediaFormat.PCMU = "PCMU"  # μ-law, 8kHz` (or L16) | 964 L; has `conversation_id` and an `on_dtmf` event handler |
| `VonageFrameSerializer` | `vonage_sample_rate: int = 16000` | — | **the one non-8 kHz outlier** |

So five of six telephony providers are 8 kHz. Against `FrameProcessorSetup.audio_in_sample_rate = 16000` / `audio_out_sample_rate = 24000`, the serializer is a permanent up/down resample pair: `_input_resampler` and `_output_resampler`, both from `create_stream_resampler(clear_after_secs=...)`. `TwilioFrameSerializer.setup()` is one line — `self._sample_rate = self._params.sample_rate or setup.audio_in_sample_rate`. **Nyquist ceiling on the wire is 4 kHz and μ-law is 8-bit companded (~2 bits/sample of dynamic range lost vs. PCM16).** Upsampling 8 k → 16 k before STT does not recover the missing band; it only satisfies the model's input contract. For Lina TMR this is the governing constraint on Korean STT accuracy — the fricative/sibilant band (ㅅ/ㅆ/ㅊ) and much of the cue for final-consonant (받침) discrimination sits at or above 4 kHz and is simply not present in the signal. Any Korean-STT number measured on 16 kHz studio audio is not transferable to this pipeline; measure on real 8 kHz μ-law or treat the number as unknown.

**Call lifecycle — identifiers.** `TwilioFrameSerializer.__init__(stream_sid: str, call_sid: str | None = None, account_sid: str | None = None, auth_token: str | None = None, region: str | None = None, edge: str | None = None, base_url: str | None = None, params: InputParams | None = None)`. Two different IDs: `stream_sid` is echoed on **every outbound media and clear message**; `call_sid` is only for REST call control. Per provider: Telnyx uses `stream_id` + `call_control_id`; Plivo `stream_id` + `call_id`; Exotel `stream_sid` + `call_sid`. `parse_telephony_websocket()` (`runner/utils.py:113`) detects the provider from the first `start` message and normalizes them to `{"stream_id", "call_id", ...}` — Telnyx's `call_control_id` is explicitly "normalized from" into `call_id`.
- **Hang-up.** `auto_hang_up: bool = True` on Twilio/Telnyx/Plivo. `__init__` raises `ValueError(f"auto_hang_up is enabled but missing required parameters: ...")` if credentials are absent. On `EndFrame`/`CancelFrame`, `serialize()` sets `_hangup_attempted = True`, calls `_hang_up_call()`, and **returns `None`** — Twilio: `POST /2010-04-01/Accounts/{account_sid}/Calls/{call_sid}.json` with `{"Status": "completed"}`, treating HTTP 404 code 20404 as already-ended; Telnyx: `POST https://api.telnyx.com/v2/calls/{call_control_id}/actions/hangup`, treating 422 code 90018 the same way. `ExotelFrameSerializer` has **no** `auto_hang_up` — it accepts `call_sid` but the docstring says "not used in this implementation."
- **Barge-in.** `InterruptionFrame` → provider-specific flush: Twilio `{"event":"clear","streamSid":...}`, Plivo `{"event":"clearAudio","streamId":...}`, Telnyx `{"event":"clear"}` (no id), Exotel `{"event":"clear","stream_sid":...}`.

**DTMF — asymmetric.** *Inbound* works everywhere: `deserialize()` on `message["event"] == "dtmf"` reads `message["dtmf"]["digit"]` and returns `InputDTMFFrame(KeypadEntry(digit))`, swallowing `ValueError` for unknown digits. `KeypadEntry(StrEnum)` (`audio/dtmf/types.py`) = `"0"`–`"9"`, `POUND = "#"`, `STAR = "*"` — 12 entries, no A/B/C/D. *Outbound* is the gap: **no telephony serializer handles `OutputDTMFFrame`**. `BaseOutputTransport.write_dtmf()` (`base_output.py:264`) branches on `_supports_native_dtmf()`, which returns `False` by default and is only overridden by the Daily transport (`DailyOutputDTMFFrame`, `session_id`/`digit_duration_ms`/`method`). For a WebSocket telephony call the fallback is `_write_dtmf_audio()` — `load_dtmf_audio(button, sample_rate=self._sample_rate)` loading `src/pipecat/audio/dtmf/dtmf-{0..9,star,pound}.wav` and pushing them as ordinary `OutputAudioRawFrame`s, i.e. **synthesized tones in the voice band**, which then get μ-law-encoded like speech. IVR navigation over Twilio therefore depends on the far-end DTMF detector hearing generated tones, not on out-of-band signalling.

- **Migration angle:** this is the piece boson-agent does not have in any form. `packages/gateway/gateway/server/` is a text-protocol WebSocket server (`GatewayWebSocketServer`, `websocket.py:35`) with no codec, no call control, and no DTMF; audio today is client-side. Migrating Lina TMR means *writing* a serializer, not porting one — and if the Korean carrier/CPaaS is not Twilio/Telnyx/Plivo/Exotel/Genesys/Vonage, budget a new `FrameSerializer` subclass (~250-300 L, per the sizes above) as a first-class deliverable. The good news is the blast radius is small and well-fenced: it touches `FastAPIWebsocketParams.serializer` and nothing else in the pipeline. Two things it collides with: boson's `gateway/interrupt/` barge-in currently reasons over partial text transcripts, whereas telephony barge-in must emit the provider `clear` event through `serialize(InterruptionFrame)`; and boson's session teardown must be reconciled with `auto_hang_up` firing on `EndFrame` (both would try to end the call). `access.py`, `history.py`, and the whole agent loop are untouched by this layer.
