# boson-agent's Agent Loop — the `while` block Pipecat wants to delete

<!-- slug: boson-agent-loop · type: boson · source: packages/basement/basement/loop/agent_loop.py, packages/basement/basement/loop/interrupt.py, packages/gateway/gateway/interrupt/cancellation.py -->

**Core Insight.** boson's think→act→observe cycle is a single 561-line async generator, `run_agent_loop(runtime, user_input) -> AsyncIterator[StreamEvent]`, that *simultaneously* owns turn bounding, message-list mutation, provider streaming, tool dispatch, hook firing, and history repair after cancellation. Nothing outside it decides when a turn ends: the turn ends when the model returns a text-only response and the function hits `break` (agent_loop.py:363). That single responsibility-cluster is exactly what Pipecat splits across a pipeline, an `LLMContext`, and two aggregators.

**Guideline.** Before porting, separate the loop's *policy* (max_turns, cancellation reconciliation, system-reminder stripping) from its *mechanics* (stream → collect tool_uses → execute → append result → re-prompt). The mechanics are free in Pipecat; the policy has no home and must be re-implemented as `FrameProcessor`s or be consciously dropped.

## Technical Details

- **Entry point.** `async def run_agent_loop(runtime: AgentRuntime, user_input: str) -> AsyncIterator[StreamEvent]` (agent_loop.py:176). Three locals alias the whole world: `ctx = runtime.context_manager`, `api = runtime.conversation_api`, `hooks = runtime.hook_registry` (L184-186). `AgentRuntime` (`schemas/runtime.py:18`) is a dataclass of 15 fields incl. `provider`, `tool_registry`, `tool_router`, `permissions`, `cancellation_flag`, `skip_user_append`, `exposed_meta_tools`, `on_tool_start` / `on_tool_end`.
- **Turn start.** `if not runtime.skip_user_append:` (L190) — pops `ctx.pop_pending_reminders()`, wraps each in `<system-reminder>…</system-reminder>`, concatenates onto `user_input`, then `ctx.add_message("user", content)` (L198). The gateway sets `skip_user_append=True` because it already appended.
- **Turn bound.** `turn_count = 0; while turn_count < runtime.config.max_turns:` (L207-209). `max_turns: int = Field(default=50, ge=1, le=1000)` (`schemas/config_schema.py:62`). The `while/else` at L365 is the exhaustion path: it yields `TextDelta(text="\n[Max turns exceeded — stopping]")` and `MessageEnd(stop_reason="max_turns")`.
- **The single inference.** L251-255:
  ```python
  async for event in runtime.provider.stream(
      messages=ctx.get_messages(),
      system=ctx.get_system_prompt(),
      tools=tools,
  ):
  ```
  Event dispatch: `TextDelta` → append to `text_parts` **and yield** (L256-258); `ToolUseStart` → append `{"id", "name", "input_json": ""}` to `tool_uses` and yield (L259-263); `InputJsonDelta` → routed by `event.tool_use_id` into the matching `tool_uses` entry, falling back to `tool_uses[-1]` when the provider left it `None` (L264-286, "v0.7.5 (#6)"); `ToolUseEnd` → `pass`; `MessageEnd` → yield.
- **Who decides the turn is complete.** Two branches, no arbiter. `if tool_uses:` (L293) → build the assistant message, execute, `continue` back to the LLM (L347). Else, text-only → `ctx.add_message("assistant", text)`, fire `POST_LLM_CALL`, `break  # Done — text response means end of turn` (L363). A third exit: cooperative cancel after a tool, `if cancellation_flag is not None and cancellation_flag.is_set: break` (L343-345).
- **Message-list maintenance is manual and Anthropic-shaped.** `Message.role` is `Literal["user", "assistant"]` only (`schemas/message_schema.py:46`) — there is **no `tool` role**; tool results are `ctx.add_message("user", [result])` carrying `ToolResultBlock(tool_use_id, content, is_error)` (agent_loop.py:540). The assistant tool-use message is assembled by hand at L316-328: strip echoed `<system-reminder>` via `re.sub(...)`, `TextBlock(text=text)` if any, then one `ToolUseBlock(id, name, input)` per call. `ContextManager.get_messages()` returns `deepcopy(self._messages)` (`context/manager.py:47-52`).
- **What the model is allowed to see is decided inside the loop.** L224-237:
  ```python
  if runtime.tool_router:
      from basement.metatool.registry import meta_tool_names
      exposed = (runtime.exposed_meta_tools
                 if runtime.exposed_meta_tools is not None else meta_tool_names())
      tools = [s for s in runtime.tool_registry.get_all_specs() if s.name in exposed] or None
  else:
      tools = runtime.tool_registry.get_all_specs() or None
  ```
  So the advertised tool array is recomputed on **every** iteration of the `while` — see [[boson-tool-router]] for why the gateway pins it under `maximize_caching`.
- **Tool execution.** `async def _execute_tool_uses(runtime, tool_uses, hooks, api, ctx)` (L393) iterates `for idx, tu in enumerate(tool_uses)` — strictly **sequential**, no parallelism. Per call: malformed-JSON short-circuit (L407-427), `PRE_TOOL_CALL` hook, dispatch (three-way: `tool_router.dispatch` / `execute_tool` for meta-tools / `execute_tool` + `runtime.permissions.check_tool` fallback, L441-459), `result.tool_use_id = tu["id"]` (L506), `POST_TOOL_CALL` hook, `ctx.add_message("user", [result])`. Queued reminders drain **after** the batch (L551-556, "Issue #42": per-tool draining orphaned later tool_uses).
- **Turn end.** `ON_TURN_END` hook (L372-376), then `if api.has_pending_compact:` fire `ON_COMPACT` with `metadata={"message_count_before": api.message_count}` (L380-389), then `await api.flush_pending()` (L390). Six hook events fire per turn: `ON_TURN_START`, `PRE_LLM_CALL`, `PRE_TOOL_CALL`, `POST_TOOL_CALL`/`ON_ERROR`, `POST_LLM_CALL`, `ON_TURN_END` (+`ON_COMPACT`).
- **Where an in-flight generation can be aborted today — two different mechanisms, neither inside the stream loop.**
  1. **Cooperative flag.** `runtime.cancellation_flag` (protocol documented at `schemas/runtime.py:41-42`: `.is_set`, `.cancel_during_tool(tool_name, arguments) -> CancelResult`). It is read at exactly two places: L344 (after a tool batch) and L513 (after one tool completes). It is **never checked between `TextDelta`s** — there is no `if cancellation_flag.is_set: break` inside the `async for event in runtime.provider.stream(...)` body. So a cooperative barge-in cannot stop token generation; it can only stop the *next* re-prompt. `gateway/interrupt/cancellation.py:171` says so verbatim: `NOTE: Cooperative — tool runs to completion, then flag is checked.`
  2. **Hard `asyncio` cancellation.** `WebSocketServer._cancel_active_task(session_id)` (`gateway/server/websocket.py:584`) calls `task.cancel()` then `await task` to drain. The `CancelledError` lands at whatever `await` the loop is parked on; if that is the provider stream, the HTTP stream really is torn down. The loop's whole cancellation-repair apparatus exists for this case: `_await_tool_boundary(awaitable, runtime, tool_uses, ctx, current_tool, completed_result=None)` (L113) wraps every tool-lifecycle await, and on `asyncio.CancelledError` calls `_reconcile_cancelled_tool_uses(...)` (L56) which pairs *every* still-unanswered `tool_use` with a synthetic `ToolResultBlock(content=f"canceled: {tu['name']}", is_error=True)` before re-raising — "Reconciliation is deliberately synchronous: once CancelledError has been caught there is no second cancellation point before history is repaired" (L70-72).
  3. **A sync tool cannot be aborted at all.** `tools/executor.py:89-113` runs sync handlers via `asyncio.create_task(asyncio.to_thread(_run_locked))` under `asyncio.shield`, and on cancel re-shields in a `while not worker.done()` loop, then raises `ToolCompletedAfterCancellation(completed)` (subclass of `CancelledError`, L33) so the real result is still committed. `_SYNC_HANDLER_LOCK = threading.Lock()` (L30) keeps sync handlers mutually exclusive.
- **The cancel bookkeeping helper.** `async def _check_cancellation_and_emit(cancellation_flag, tool_name: str, tool_input: dict, ctx, result_blocks: list | None = None) -> bool` (L139). It calls `cancellation_flag.cancel_during_tool(tool_name, tool_input)`, commits `result_blocks` first as ONE user message so every assistant `tool_use` keeps a matching `tool_result`, and merges a leading user-role cancel entry into that same message as a `TextBlock` — "mirroring the merged-blocks shape of `InterruptHandler.handle_barge_in`, which preserves strict assistant→user role alternation (some models reject consecutive same-role messages)" (L152-156). Same pattern on the `ToolCompletedAfterCancellation` branch (L460-479), which commits the real result plus `f"canceled: {rest['name']}"` blocks for the un-executed batch mates, then `raise asyncio.CancelledError() from completed`.
- **`loop/interrupt.py` is NOT the barge-in module — expectation violated.** It is 57 lines: `class InterruptHandler` with `setup()` registering a **SIGINT** handler (`signal.signal(signal.SIGINT, self._on_sigint)`, L31), `is_interrupted` property, `get_context_message() -> "[Response interrupted by user]"`, `reset()`, `teardown()`. It is a CLI-only Ctrl+C facility used by `basement/__main__.py:181-186`, which checks `interrupt.is_interrupted` *between yielded events* and breaks out of the `async for`. The real voice barge-in lives in a different package and a different class of the same name: `gateway/interrupt/handler.py:51` (`InterruptHandler.handle_barge_in(session, content, partial_agent_output, tagging=True, tool_cancel=None)`), plus `gateway/interrupt/cancellation.py:21` (`CancellationFlag` with `stash_tool_cancel` / `consume_tool_cancel`) and `policy.py` / `detector.py` / `fillers.py`.
- **Migration angle:** `run_agent_loop` has no Pipecat counterpart to port *into* — it is dissolved. (a) The `while turn_count < max_turns` block is replaced by the frame topology of [[function-calling]]: one `LLMContextFrame` → one inference → `run_function_calls()`, and the re-prompt comes from `LLMAssistantAggregator` pushing `LLMContextFrame` **upstream**. Pipecat has **no `max_turns`**, so the L207-209 guard and the L365 `while/else` warning path must be rebuilt as a counting `FrameProcessor` or dropped. (b) All `ctx.add_message(...)` calls (L198, L328, L355, L426, L475, L540, L556) collide head-on with `LLMContext.add_message` + the aggregator pair ([[llm-service-context]]); the `role in {"user","assistant"}` + `ToolResultBlock`-in-a-user-message convention must be re-expressed as OpenAI-shaped `{"role": "tool", "tool_call_id": ...}` dicts, which is a real schema rewrite, not a rename. (c) The `AsyncIterator[StreamEvent]` contract disappears: `TextDelta`/`ToolUseStart`/`MessageEnd` become `LLMTextFrame` / `FunctionCallInProgressFrame` / `LLMFullResponseEndFrame` pushed downstream, so `gateway/core.py:323`'s `async for event in run_agent_loop(runtime, content)` — including its system-reminder tail-buffer scrubber (L305-389) — becomes a `FrameProcessor` sitting between LLM and TTS. (d) **Interruption is the one place Pipecat is strictly better**: boson today cannot abort mid-generation cooperatively (flag checked only at L344/L513), whereas Pipecat propagates `InterruptionFrame` through every processor and marks `FunctionCallInProgressFrame` / `FunctionCallResultFrame` `UninterruptibleFrame` so results still land. `_reconcile_cancelled_tool_uses` (L56) and `_await_tool_boundary` (L113) are ~80 lines that mostly evaporate. (e) **Untouched:** the hook system (`hooks/runner.fire_event`, 6 events) has no Pipecat analogue and must map onto `llm.event_handler(...)` + processor placement; `ContextManager.pop_pending_reminders()` and the `<system-reminder>` protocol have no home at all.
