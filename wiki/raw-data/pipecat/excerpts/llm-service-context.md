# LLM Service + Context Aggregator Pair — who owns the message list

<!-- slug: llm-service-context · type: source · source: src/pipecat/services/llm_service.py, src/pipecat/processors/aggregators/llm_context.py, llm_response_universal.py, llm_response.py, gated_llm_context.py -->

**Core Insight.** The message list is owned by a single plain `LLMContext` object that application code constructs and keeps a reference to. The LLM service owns *nothing* — it is stateless with respect to conversation history and reads whatever `LLMContext` arrives on an `LLMContextFrame`. Two `FrameProcessor`s straddling the LLM (the user aggregator upstream, the assistant aggregator downstream) mutate that one shared object in place; the "conversation" is an emergent property of frames circulating around a loop, not of any object's internal loop.

**Guideline.** Put the mutation of history in the aggregators and the *possession* of history in `LLMContext`. If you need to inject, rewrite, or gate messages, do it by (a) holding the `LLMContext` reference yourself and calling `add_message` / `set_messages` / `transform_messages`, or (b) pushing `LLMMessagesAppendFrame` / `LLMMessagesUpdateFrame` / `LLMMessagesTransformFrame` at an aggregator. Never subclass the LLM service to hold state.

## Technical Details

- **Owner: `LLMContext`** (`llm_context.py:83`). State is exactly three fields set in `__init__` (L110-112): `self._messages: list[LLMContextMessage]`, `self._tools: ToolsSchema | NotGiven`, `self._tool_choice`. Mutators: `add_message(message)` L361, `add_messages(messages)` L369, `set_messages(messages)` L377 (`self._messages[:] = messages` — mutates in place so every holder of the reference sees it), `transform_messages(transform)` L385, `set_tools` L396, `set_tool_choice` L408, plus `async add_image_frame_message` L416 / `add_audio_frames_message` L440.
- **`get_messages(llm_specific_filter=None, *, truncate_large_values=False)`** L221 returns the *live* list, not a copy, when unfiltered (`messages = self._messages`, L245). Only `truncate_large_values=True` deep-copies. `LLMContextMessage = LLMStandardMessage | LLMSpecificMessage`, where the standard form is aliased to OpenAI's `ChatCompletionMessageParam` under `TYPE_CHECKING` only (L55-65) and is a plain dict at runtime.
- **The pair: `LLMContextAggregatorPair(context, *, user_params, assistant_params, add_tool_change_messages, realtime_service_mode)`** (`llm_response_universal.py:2251`). It constructs `LLMUserAggregator(context, params=user_params, ...)` (L2296) and `LLMAssistantAggregator(context, params=assistant_params, ..., _paired_user_aggregator=self._user)` (L2309) over **the same context object**. Accessors `user()` L2316 / `assistant()` L2324, and `__iter__` L2332 permits `user_agg, assistant_agg = LLMContextAggregatorPair(context)`.
- **Shared base `LLMContextAggregator(FrameProcessor)`** L365, `__init__(*, context, role, add_tool_change_messages)` L388. Exposes `messages` (L455), `role` (L464), `context` (L473), `_get_context_frame() -> LLMContextFrame` (L481), `push_context_frame(direction=DOWNSTREAM)` (L489), and the abstract `push_aggregation() -> str` (L546).
- **User half (before the LLM).** `LLMUserAggregator` L563. `process_frame` L785 consumes `TranscriptionFrame` (L808-809, *not* forwarded — interim/translation frames also swallowed L810-813), and on turn end `push_aggregation()` L856 does exactly:
  ```python
  aggregation = self.aggregation_string()
  await self.reset()
  self._context.add_message(cast(LLMContextMessage, {"role": self.role, "content": aggregation}))
  await self.push_context_frame()          # DOWNSTREAM → reaches the LLM service
  ```
  It also handles `LLMRunFrame`, `LLMMessagesAppendFrame`, `LLMMessagesUpdateFrame`, `LLMMessagesTransformFrame`, `LLMSetToolsFrame` (normalize → `_maybe_add_tool_change_messages` → `set_tools`, L822-834) and `LLMSetToolChoiceFrame`.
- **Assistant half (after the LLM, physically last in the pipeline).** `LLMAssistantAggregator` L1384, `process_frame` L1538. `push_aggregation()` L1677 appends `{"role": "assistant", "content": aggregation}` (L1685), pushes a context frame, then a `LLMContextAssistantTimestampFrame`. It also writes the *tool* half of history:
  - `_handle_function_call_in_progress` L1747 → appends an assistant message carrying `tool_calls: [{id, function:{name, arguments}, type:"function"}]` (L1753-1767), then a placeholder `{"role": "tool", "content": "IN_PROGRESS", "tool_call_id": ...}` (L1773-1779) for sync calls, or `async_tool_messages.build_started_message(...)` for async ones.
  - `_handle_function_call_result` L1783 → `_handle_function_call_finished` L1908 → `_update_function_call_result` L2157, which **rewrites the placeholder in place**: it walks `self._context.get_messages()` and assigns `message["content"] = result` on the matching `tool_call_id`. This only works because `get_messages()` hands back the live dicts.
  - Then `_maybe_push_context_after_function_result` L1859 pushes `LLMContextFrame` **UPSTREAM** (L1889) — deferring while more `FunctionCallResultFrame`s are queued (`has_queued_frame`, L1870) or the bot is still speaking (L1878-1886, resumed on `BotStoppedSpeakingFrame` at L1618-1620).
- **The service holds no history.** `LLMService.process_frame` L679 handles `InterruptionFrame`, `LLMConfigureOutputFrame`, `LLMUpdateSettingsFrame`, `LLMContextSummaryRequestFrame`; the only context work is L712-723, `self._sync_registered_tool_handlers(frame.context.tools)`. `OpenAIBaseLLMService.process_frame` (`services/openai/base_llm.py:590`) is the pattern: on `LLMContextFrame`, push `LLMFullResponseStartFrame`, `await self._process_context(frame.context)`, push `LLMFullResponseEndFrame`. History is read just-in-time through the adapter.
- **Not the context aggregator:** `llm_response.py` is now 86 lines and contains only `LLMFullResponseAggregator(FrameProcessor)` (L20) — a token collector between `LLMFullResponseStartFrame`/`LLMFullResponseEndFrame` that fires an `on_completion` event. All the base aggregator classes that used to live here (`LLMUserContextAggregator`, `LLMAssistantContextAggregator`, …) were removed.
- **`GatedLLMContextAggregator`** (`gated_llm_context.py:14`) is the hold-the-turn primitive: `__init__(*, notifier: BaseNotifier, start_open: bool = False)`. It stores only the **latest** `LLMContextFrame` (`self._last_context_frame = frame`, L56) and releases it from `_gate_task_handler` L76 after `await self._notifier.wait()`. Stale contexts are dropped, not queued.
- **Expected-but-absent:** there is **no `create_context_aggregator()`** anywhere in `src/` at this commit. `grep -rn "create_context_aggregator" src/ examples/` returns nothing; the only hits are in `CHANGELOG.md` documenting its removal from `LLMService`, `OpenAILLMService`, `AnthropicLLMService`, `AWSBedrockLLMService` alongside `OpenAILLMContext` itself (PR #4215). The replacement is `LLMContext(messages, tools)` + `LLMContextAggregatorPair(context)`. Any tutorial showing `llm.create_context_aggregator(context)` is pre-1.x and will not run.
- **Canonical wiring** (`examples/function-calling/function-calling-openai.py:101-117`) — note the assistant half sits *after* `transport.output()`:
  ```python
  context = LLMContext(tools=[get_current_weather, get_restaurant_recommendation])
  user_aggregator, assistant_aggregator = LLMContextAggregatorPair(
      context, user_params=LLMUserAggregatorParams(vad_analyzer=SileroVADAnalyzer()))
  pipeline = Pipeline([transport.input(), stt, user_aggregator, llm, tts,
                       transport.output(), assistant_aggregator])
  ```
- **Migration angle:** This directly replaces `basement/context/manager.py::ContextManager` (`packages/basement/basement/context/manager.py:21`), whose `_messages: list[Message]` is the same working memory. Two concrete collisions: (1) boson's `ContextManager.get_messages()` returns `deepcopy(self._messages)` "to prevent external mutation" (L47-51) — Pipecat's `get_messages()` deliberately returns the live list *because* the assistant aggregator mutates tool-result messages in place; a defensive-copy port would silently break `_update_function_call_result`. (2) boson's messages are `basement.schemas.message_schema.Message` pydantic objects; `LLMContext` stores plain dicts and delegates provider shaping to adapters, so the `Message`/`ContentBlock` schema layer becomes dead weight, not a translation target. `ctx.add_message("user", content)` in `run_agent_loop` (`packages/basement/basement/loop/agent_loop.py:198`) is replaced by `LLMUserAggregator.push_aggregation()`; `ctx.get_system_prompt()` has no `LLMContext` equivalent — the system prompt moves to `Service.Settings(system_instruction=...)` or a leading `{"role": "system"}` message that adapters extract via `_extract_initial_system`. `pop_pending_reminders()` / system-reminder injection has no Pipecat home and must become a custom `FrameProcessor` (see [[custom-processor-guide]]).
