# Pipecat's Stated Philosophy — thin on manifesto, thick on enforced convention

<!-- slug: pipecat-design-philosophy · type: doc · source: AGENTS.md, README.md, CONTRIBUTING.md, COMMUNITY_INTEGRATIONS.md, CHANGELOG.md, changelog/, src/pipecat/utils/deprecation.py, scripts/deprecations/deprecations.json -->

**Core Insight.** Pipecat has **no architecture document, no design document, and no non-goals section** — I looked; `*.md` at the repo root is exactly `AGENTS.md`, `CHANGELOG.md`, `CLAUDE.md`, `COMMUNITY_INTEGRATIONS.md`, `CONTRIBUTING.md`, `README.md`, `SECURITY.md`, and a `find` for `*architect*`/`*design*`/`*philosoph*` returns nothing. `CLAUDE.md` is one line: `@AGENTS.md`. The stated "why" is five README bullets. But the *enforced* philosophy is unusually heavy: conventions are compiled into a machine-parseable deprecation grammar, a generated registry, and a test suite that fails the build when prose drifts. Pipecat's design intent lives in `AGENTS.md` and in `pytest`, not in an essay.

**Guideline.** Read `AGENTS.md` as the spec and the deprecation registry as the roadmap — not the README. When writing a processor or service, the only hard rules the repo actually states are: call `super().process_frame()`, push frames in the direction they arrived, never call raw `asyncio.create_task()`, and report failures with `push_error(..., fatal=False)` rather than raising. Everything else is pattern-matching against existing services.

## Technical Details

### What it claims to be — and the one thing it refuses

- **Claim** (`AGENTS.md:7`): *"Pipecat is an open-source Python framework for building real-time voice and multimodal conversational AI agents. It orchestrates audio/video, AI services, transports, and conversation pipelines using a frame-based architecture."* `pyproject.toml:8` is blunter: *"An open source framework for voice (and multimodal) assistants."* BSD-2-Clause, `requires-python = ">=3.11"`, `Development Status :: 5 - Production/Stable`.
- **The five stated virtues** (`README.md:23-29`, verbatim): Voice-first; **Pluggable**: *"Supports many AI services and tools"*; **Composable Pipelines**: *"Build complex behavior from modular components"*; **Multi-Agent Ready**: *"Each pipeline is an agent"*; Real-Time.
- **The only explicit refusal in the repo** is governance, not architecture (`COMMUNITY_INTEGRATIONS.md:9-11`): *"**What we don't do:** The Pipecat team does not code review, test, or maintain community integrations."* … *"**Why this approach:** This allows the community to move quickly while keeping the Pipecat core team focused on maintaining the framework itself."* Pipecat refuses to be the maintainer of its own long tail — 73 dirs under `src/pipecat/services/`, 87 optional-dependency extras in `pyproject.toml`. Community packages are named `pipecat-{vendor}`, classes `VendorLLMService` / `VendorHttpTTSService` / `VendorFrameSerializer` (`COMMUNITY_INTEGRATIONS.md:245-263`).
- **Honest gap:** nowhere does the repo say what Pipecat is *not* architecturally — no "we are not an agent framework", no "we don't do orchestration". That negative space is undefended and you should not assume it.

### The processor / service contract, as actually written

Explicit rules, all from `AGENTS.md`:

- **Direction default** (`:207`, in the 7-step "Service Implementation" list): *"By default, all frames should be pushed in the direction they came"* — the closest thing to a frame contract in the docs. Also `:56`: frames *"Flow DOWNSTREAM (input→output) or UPSTREAM (acknowledgments/errors)"*, matching `FrameDirection(Enum)` at `frame_processor.py:60-69` (`DOWNSTREAM = 1`, `UPSTREAM = 2` — only two).
- **Task management** (`:109`): *"**Always** use `self.create_task(coroutine, name)` instead of raw `asyncio.create_task()`. The `TaskManager` automatically tracks tasks and cleans them up on processor shutdown."* This is the single most emphatic MUST in the file.
- **Error handling** (`:111`): *"Use `await self.push_error(msg, exception, fatal)` to push errors upstream. Services should use `fatal=False` (the default) so application code can handle errors and take action (e.g. switch to another service)."* Real signature at `frame_processor.py:864-871`: `push_error(self, error_msg: str, exception: Exception | None = None, fatal: bool = False, category: ErrorCategory | None = None, force_treat_as_permanent: bool = False)`.
- **Event handlers** (`:107`): handlers run in a background task by default; `sync=True` handlers *"need to execute fast."*
- **Interruption is a broadcast any processor may trigger** (`:103`): *"any processor can trigger one by calling `await self.broadcast_interruption()`, which broadcasts an `InterruptionFrame` both upstream and downstream."*
- **Dataclass vs Pydantic is a hard split** (`:143`): `@dataclass` for *"Frame types, context aggregator pairs, internal data containers"*; Pydantic `BaseModel` for *"Service `InputParams`, transport/VAD/turn params, metrics data, API request/response models, serializer params."* Rationale given: frames are *"high-frequency, no validation needed."*
- **What a processor may NOT do is never stated as a prohibition.** There is no "a processor must not block", no "must not hold state across turns", no ordering rule for composing a pipeline. `Pipeline.__init__` (`pipeline/pipeline.py:99-121`) just does `self._processors = [self._source, *processors, self._sink]` then `_link_processors()` — **composition order is literal list order and nothing validates it.** STT-before-LLM-before-TTS is convention carried by `examples/`, not a checked constraint. The `super().process_frame()` requirement is real but documented only implicitly (base impl at `frame_processor.py:820-847` does lifecycle work and observer notification, and does *not* push the frame).

### What the changelog reveals: an aggressive-rename, deferred-removal culture

- `CHANGELOG.md:3-6`: *"The format is based on Keep a Changelog … and this project adheres to Semantic Versioning."* Towncrier fragments in `changelog/` (203 files pending at this commit: 68 `.fixed`, 60 `.added`, 56 `.changed`, **11 `.deprecated`, 3 `.removed`**, 5 `.performance`). Release cadence is fast: 1.0.0 (2026-04-14) → 1.7.0 (2026-08-01), seven minors in under four months.
- **1.0.0 was a mass amputation**, ~380 lines of `⚠️ Removed` — `TTSService.say()` ("Push a `TTSSpeakFrame` instead"), `LLMService.request_image_frame()` ("Push a `UserImageRequestFrame` instead"), `FrameProcessor.wait_for_task()`, `StartInterruptionFrame`/`BotInterruptionFrame`, `KrispFilter`, `NoisereduceFilter`, single-argument function calls, and a dozen module relocations. **The pattern is unmistakable: every removed imperative method was replaced by "push a frame."** The framework has been steadily converting its own API surface from method calls into frames.
- **1.3.0 renamed the top-level noun**: `PipelineTask` → `PipelineWorker`, `PipelineTaskParams` → `WorkerParams`, `PipelineRunner` → `WorkerRunner` (moved to `pipecat.workers.runner`), `FrameProcessor.pipeline_task` → `.pipeline_worker`. `AGENTS.md:82` states the reason as vocabulary hygiene: *"a 'worker' is a runnable unit, 'task' now refers only to asyncio tasks, and cross-worker RPC uses 'jobs' and 'job groups'."* Old names still resolve as aliases.
- **The registry is the real stability signal.** `scripts/deprecations/deprecations.json` is auto-generated (*"DO NOT EDIT BY HAND"*) from source directives: **391 live deprecations, and `removed_in == "2.0.0"` for all 391.** By kind: 268 parameters, 88 classes, 24 methods, 6 modules, 3 properties, 2 functions. By relation: **375 `use_existing`, 4 `move`, 1 `rename`, and only 11 `none`** — 97% have a named replacement. By vintage: 245 date to **0.0.105** (the `InputParams`/`params` → `Settings` dataclass migration, e.g. `AnthropicLLMService.InputParams` → `AnthropicLLMService.Settings`), 46 to the unreleased **1.8.0**. Sibling `removals.json` is empty.
- **Read that carefully: 245 deprecations from 0.0.105 survived the 1.0.0 major bump.** 1.0.0 removed a curated batch and deliberately carried the rest forward. So "1.0.0 = stable" is only half-true — the API is *additively* stable and behaviorally solid, but a 2.0.0-sized cliff is already fully enumerated and dated. Anyone building on 1.x today can read their exact future breakage out of that JSON file.
- **In-flight 1.8.0 deprecations show where the design is still moving**: `ErrorFrame.fatal`, `FatalErrorFrame`, and `push_error(fatal=)` are all going (`changelog/5348.deprecated.md`: *"A fatal error would cancel the pipeline outright; that's now an application decision"*, replaced by `force_treat_as_permanent=True` + `PipelineWorker.processor_unusable_policy`, or `ErrorFrame` followed by `EndWorkerFrame`). Seven `StartFrame` config fields (`audio_in_sample_rate`, `enable_metrics`, `tracing_context`, …) move to `FrameProcessorSetup` read in `setup()` (`changelog/5316.deprecated.md`) — **frames are being purged of configuration so they carry only data.**

### Philosophy compiled into tests

- `src/pipecat/utils/deprecation.py:13` fixes one canonical string: `` `Subject` is deprecated since X.Y.Z and will be removed in A.B.C. Use `Replacement` instead. `` — and `:15-19` states the commitment: *"the removal version A.B.C is a concrete semantic version (e.g. 2.0.0) — **we commit to the release that removes it rather than saying 'a future release'** — and the second sentence is `No replacement.` when there is nothing to migrate to, stated explicitly and never omitted."*
- Enforced by `DEPRECATION_MESSAGE_RE` (`:80-84`) and `tests/test_deprecation_markers.py`, whose tests include `test_directives_state_removal_version`, `test_deprecated_subject_names_decorated_symbol`, `test_deprecated_version_matches_docstring_directive`, `test_deprecated_replacement_targets_exist` (the replacement must actually exist), and `test_deprecations_registry_is_up_to_date`. In src: 399 `.. deprecated::` directives, 112 PEP-702 `@deprecated` decorators, 95 literal "will be removed in 2.0.0".
- **`AGENTS.md:192-198` "Writing for Future Readers"** is the repo's sharpest prose rule: *"every sentence must answer 'what does the code do now?' — not 'what happened while we worked on it.' … If a sentence describes a superseded implementation, a rejected alternative, verification performed, or argues the change is correct, delete it."*
- **Bug-report policy** (`CONTRIBUTING.md:39-66`): *"A good bug report is one a maintainer can act on. The single most useful thing you can include is a **minimal runnable reproduction**"* — a `run_test()` case from `pipecat.tests.utils` or a failing behavioral eval. `needs-repro` auto-closes at 30 days. On AI-generated reports: *"Using AI tools to help write a report is fine. Submitting AI output you haven't verified is not."*
- **Two-tier testing** (`AGENTS.md:214-223`): `run_test()` for frame plumbing; `pipecat.evals` YAML scenarios driving a *real bot* over RTVI for behavior — *"use it to confirm a feature works (interruptions, function calls, vision, multi-turn, transcription, DTMF) rather than only checking frame plumbing."*

- **Migration angle:** Six boson habits fight this grain, ranked by cost. **(1) `asyncio.create_task` / `asyncio.shield`** — `tools/executor.py:89-113` spawns raw tasks and re-shields in a `while not worker.done()` loop. This violates the one emphatic MUST in `AGENTS.md:109`; `TaskManager` will not track them, so they outlive processor shutdown and leak across sessions. Mechanical fix, but every site must be found. **(2) Exceptions as control flow** — boson raises `ToolCompletedAfterCancellation(CancelledError)` to unwind ([[boson-agent-loop]]). Pipecat's contract is *return a frame*: `push_error(..., fatal=False)` upstream so an application-level `ServiceSwitcher` can fail over. A raised exception kills the processor's task instead of producing an `ErrorFrame`. And porting to `fatal=True` aims at a target already deprecated in 1.8.0 — go straight to `force_treat_as_permanent=True` or `ErrorFrame` + `EndWorkerFrame`. **(3) Yield-based streaming** — `AsyncIterator[StreamEvent]` is a *pull* contract with exactly one consumer; Pipecat is *push* with fan-out to observers, RTVI, and metrics. Every `yield` becomes `push_frame`, and boson's single-consumer assumptions (the gateway's system-reminder tail-buffer scrubber) break. **(4) Direct context mutation** — boson's scattered `ctx.add_message(...)` is precisely the anti-pattern 1.0.0 added `LLMMessagesTransformFrame` to kill: the changelog says the old snapshot-and-overwrite approach means *"what if there had already been a change to the context queued in the pipeline? The transformed messages would simply overwrite it."* Port to `LLMContext` + `LLMContextAggregatorPair`, not to a mutable handle. **(5) Config riding on frames** — if boson's port stuffs per-turn configuration into frame payloads it fights `AGENTS.md:143` (frames are `@dataclass`, config is Pydantic) *and* the active 1.8.0 direction of stripping config off `StartFrame` into `FrameProcessorSetup`. **(6) Version pinning** — boson's provider wrappers are exactly the "community integration" Pipecat explicitly will not review, test, or maintain, and any wrapper written as `XLLMService(model=..., params=...)` is already on the 0.0.105-deprecated path among the 245 records headed for 2.0.0. Write them against `Settings` from day one, name them `VendorLLMService`, and treat `deprecations.json` as the migration backlog. **One free win:** boson's `max_turns` guard has no Pipecat counterpart to conflict with — Pipecat states no turn limit anywhere, so it must be rebuilt as a counting `FrameProcessor` or consciously dropped.
