# Pipecat Flows Actions — a 3-verb side-effect vocabulary bolted onto node transitions

<!-- slug: flows-actions · type: source · source: src/pipecat/flows/actions.py (400 L), src/pipecat/flows/adapters.py (68 L), src/pipecat/flows/types.py, src/pipecat/flows/manager.py -->

**Core Insight.** Pipecat Flows ships **exactly three built-in action types** — `tts_say`, `end_conversation`, `function` — and the third is a deliberate escape hatch that makes the other two nearly redundant. Actions are *not* a control-flow language: they cannot choose the next node, cannot veto a transition, and cannot return a value. Node selection is owned entirely by function return values (`ConsolidatedFunctionResult`'s second tuple element), so an "action" in Flows means only "a side effect scheduled at a known point in the pipeline." The framework's own comment says the direction of travel is *away* from custom action types: "we're de-emphasizing custom actions in favor of `function` actions, which should meet most needs" (`actions.py:293-294`).

**Guideline.** Use `{"type": "function", "handler": fn}` for anything that is not literally speaking a line of text. Register nothing globally unless you need the same verb across many nodes — inline `handler` in the `ActionConfig` self-registers. And never encode a state transition as an action: put it in the function's return tuple.

## Technical Details

- **The complete built-in vocabulary** — three `_register_action` calls in `ActionManager.__init__` (`actions.py:104-106`), and that is the entire list:
  ```python
  self._register_action("tts_say", self._handle_tts_action)
  self._register_action("end_conversation", self._handle_end_action)
  self._register_action("function", self._handle_function_action)
  ```
  - `tts_say` (`_handle_tts_action`, L302) — requires `text`; optional `append_text_to_context: bool = True`. Queues `TTSSpeakFrame(text=..., append_to_context=...)` then an `ActionFinishedFrame()`. Missing `text` logs an error and returns — it does **not** raise.
  - `end_conversation` (`_handle_end_action`, L334) — optional `text` goodbye line (also honors `append_text_to_context`), then queues `EndFrame()`. Deliberately queues **no** `ActionFinishedFrame`: "the previously-queued `EndFrame` ensures that it'll never get delivered to our observer" (L361-362). `execute_actions` `break`s after this type (L218-219) so nothing later in the list runs.
  - `function` (`_handle_function_action`, L364) — requires `handler`; queues `FunctionActionFrame(action=action, function=handler)`, a `ControlFrame` dataclass (L49-59). The handler runs *not* at queue time but when the frame reaches the pipeline's downstream end, in `on_frame_reached_downstream`: `await frame.function(frame.action, flow_manager)` (L117).
- **There is no `transition` / `set_node` / `inject_message` / `log` / `webhook` action.** I looked for them; they do not exist. Everything beyond speech and hangup is expressed as `type: "function"`.
- **Custom action registration, two routes.**
  1. Explicit: `FlowManager.register_action(action_type: str, handler: Callable)` (`manager.py:353`), which forwards to `ActionManager._register_action`. Raises `ValueError("Action handler must be callable")` for non-callables (`actions.py:139-140`).
  2. Implicit from config: `_register_action_from_config(action)` (`manager.py:370`) runs over both `pre_actions` and `post_actions` at the top of `set_node` (L639-644). If the type is unknown and `handler` is present it self-registers; if unknown and no handler it raises `ActionError(f"Action '{action_type}' not registered. Provide handler in action config or register manually.")`.
  `ActionConfig` is a `TypedDict(total=False)` with `type: Required[str]`, `handler`, `text`, `append_text_to_context` — and "Additional fields are allowed and passed to the handler" (`types.py:112-131`), so arbitrary payload keys ride along in the same dict. See [[flows-node-types]] for the surrounding type vocabulary.
- **Handler signature is arity-sniffed, and both sync and async are supported.** `execute_actions` calls `inspect.signature(handler)` and sets `can_handle_flow_manager_arg = len(sig.parameters) > 1` (L181-182), then branches on `asyncio.iscoroutinefunction(handler)` (L192, L206). Modern shape is `FlowActionHandler = Callable[[dict[str, Any], "FlowManager"], Awaitable[None]]` (`types.py:98`); the 1-arg `LegacyActionHandler` is deprecated since 1.5.0 and emits a one-shot `DeprecationWarning` (L197-205). **Quirk worth knowing:** the built-ins are registered as *bound methods* whose signature is `(action)` after `self` is bound — verified `len(sig.parameters) == 1` — so Pipecat's own `tts_say` takes the legacy branch and trips its own deprecation warning.
- **Pre vs post — and what "pre" actually precedes.** `NodeConfig` declares `pre_actions: list[ActionConfig]` / `post_actions: list[ActionConfig]`, documented as "before/after LLM inference" (`types.py:200-201`). In `_set_node` the real ordering is: register handlers → **pre_actions** (L647-648) → build function schemas → `_update_llm_context(...)` (L693) → set `_current_node` → queue `LLMRunFrame()` (L709) → **post_actions** (L712-714). So pre-actions run *after the transition is already committed to* but *before the new node's messages and tools are installed* — see [[flows-state-machine]] for the surrounding `_set_node` machinery.
- **Can an action block a transition?** There is no veto API, but there is an error path: a raising handler is wrapped as `ActionError(f"Failed to execute action {action_type}: {str(e)}")` (L224), which propagates out of `_set_node`'s `try` and is re-raised as `FlowError(f"Failed to set node {node_id}")` (L723). Because pre-actions run before `_update_llm_context`, a raising pre-action leaves `self._current_node` untouched — the node is effectively aborted. Post-action failures cannot un-set the node.
- **Blocking *within* a batch is type-dependent, not user-configurable.** `_maybe_wait_for_ongoing_actions_to_finish(previous_action_type, upcoming_action_type)` (L249) encodes a hard-coded pipeline-position table — the reasoning is that a frame's effect lands at a fixed depth in the pipeline, so you only wait when the next thing acts *earlier*:

  | previous action | upcoming action | waits? |
  |---|---|---|
  | `tts_say` | `tts_say` / `end_conversation` / `function` | no — effect at same point or later |
  | `tts_say` | custom type, or `None` (end of batch) | **yes** (L277) |
  | `function` | anything, including `None` | **yes, always** (L285) |
  | custom type | anything | no — never (L286-294) |
  | `None` (first action) | anything | no |

  The custom-type row is a deliberate gap: "we could, in the future, add new API affordances for users to tell us to wait ... But let's hold off ... since we're de-emphasizing custom actions" (L288-294). Bookkeeping is a counter plus an `asyncio.Event`: `_increment_ongoing_actions_count` clears the event on 0→1, `_decrement_ongoing_actions_count` sets it on 1→0 (L390-400). The decrement is driven by frames arriving downstream, not by the handler returning.
- **Deferred post-actions.** When `respond_immediately=False`, post-actions are not run inline; `schedule_deferred_post_actions` stashes them (L230) and they fire on the next `BotStoppedSpeakingFrame` **only if** `self._ongoing_actions_count == 0` — "a `BotStoppedSpeakingFrame` only indicates that the bot's turn is over if there are no ongoing actions (otherwise one of those actions may have been responsible for it)" (L120-124). `set_node` clears any stale deferred list first (L636).
- **`adapters.py` is not what its name suggests.** I expected a per-LLM-provider function-schema adapter; **it is not that**. `flows/adapters.py` contains a single 2-method class, `LLMAdapter`, with `format_summary_message(self, summary: str) -> dict` (returns `{"role": "developer", "content": f"Here's a summary of the conversation:\n{summary}"}`) and `async generate_summary(self, llm, summary_prompt, context) -> str | None` (one-shot out-of-band `await llm.run_inference(summary_context, system_instruction=summary_prompt)`). Its only consumer is `ContextStrategy.RESET_WITH_SUMMARY`, under a 5-second `asyncio.wait_for` that silently falls back to `APPEND` on timeout or empty summary (`manager.py:799-822`) — and that strategy is itself `.. deprecated:: 1.5.0` in favor of pushing `LLMSummarizeContextFrame` from a pre-action. **Real per-provider schema conversion lives elsewhere**, in `src/pipecat/adapters/` (`BaseLLMAdapter`, `to_provider_tools_format`) — see [[function-calling]]. Flows sidesteps it entirely by emitting a provider-neutral `ToolsSchema(standard_tools=[...])` (`manager.py:670-672`).
- **Migration angle:** boson's `gateway/schemas/actions.py` (80 L) defines an 8-verb vocabulary — `ActionType = Literal["continue", "respond", "inject", "compact", "pre_tool", "stage_transition", "filter", "pass"]` — over a flat `@dataclass Action(type, payload: dict)`. Pipecat's `ActionConfig(type, handler, ...)` is the same shape (tagged dict, open payload), so the *mechanism* ports 1:1, but the vocabulary does not survive intact:

  | boson `Action` | Pipecat Flows equivalent | fidelity |
  |---|---|---|
  | `Respond(text)` | `{"type": "tts_say", "text": ..., "append_text_to_context": True}` | clean 1:1 |
  | `PreTool(tool_name, arguments, preamble)` | `pre_actions=[{"type": "function", "handler": fn}]` | good; `preamble` becomes a preceding `tts_say` — note the wait table means `tts_say`→`function` does **not** serialize |
  | `StageTransition(target_stage)` | **not an action.** Second element of a function's return tuple, or `await flow_manager.set_node_from_config(node)` | structural rewrite |
  | `Inject(content)` | no built-in; a `function` action queuing a context-mutating frame, or fold into the next node's `task_messages` | manual |
  | `Compact()` | `ContextStrategyConfig(strategy=RESET_WITH_SUMMARY, ...)` (deprecated) or `LLMSummarizeContextFrame` from a pre-action | semantics differ — Flows blocks with a 5 s cap; boson is "async ... in background" |
  | `Continue()` / `Pass()` / `Filter(reason)` | **none.** Pre-LLM routing verdicts belong in an upstream `FrameProcessor` | no home |

  The `StageTransition` row is the single biggest change: boson lets a *rule* move the stage machine; Pipecat only lets a *tool call* (or an out-of-band `set_node_from_config`) move the node. And everything under `layers/01-filler-filter/rules` — the `Filter`/`Pass` verdicts — must be rewritten as processors, because by the time an action runs the message is already in the context.
  Also: boson's `RuleEngine` collects actions from many checks and arbitrates ("every non-transition action from every check survives", `rules/engine.py:95-99`), splitting sequential vs parallel checks and picking a winner. Pipecat has **no arbiter** — `execute_actions` is a straight `for` loop over one node's declared list, and the first exception aborts the rest of the batch.
