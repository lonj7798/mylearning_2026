# The Bus as Side Channel — and the two telephony extensions built without it

<!-- slug: bus-and-extensions · type: source · source: src/pipecat/bus/, src/pipecat/registry/, src/pipecat/extensions/ivr/, src/pipecat/extensions/voicemail/ -->

**Core Insight.** The bus is **not** a second pipeline and **not** a shared-state store. It is name-addressed pub/sub between *workers* (separate pipelines, possibly separate processes) where the unit is a `BusMessage` dataclass, delivery is a one-way callback (`async def on_bus_message(self, message) -> None`, `subscriber.py:25`), and there is **no read API** — no `bus.get()`, no snapshot, no query. You cannot ask the bus what the current state is; you can only be told when something happened. The two shipped telephony extensions prove the corollary: IVR and voicemail both need one component to inform a *non-adjacent* component, and **neither touches the bus**. They pass shared `BaseNotifier` objects to both constructors.

**Guideline.** Reach for the bus only when the recipient is a different **worker**, or when you need request/response with a status (jobs). For "component A must tell non-adjacent component B in the same pipeline," the framework's own answer is a shared `EventNotifier` — see `VoicemailDetector`'s three-notifier construction. For "component B must *read* current state," use a shared plain object (the `LLMContext` pattern), not messages.

## Technical Details

### What the bus really is

- `WorkerBus(BaseObject)` — `bus/bus.py:49`. One abstract method: `async def publish(self, message: BusMessage) -> None` (L142). `async def send(...)` (L127) short-circuits `BusLocalMessage` straight to `on_message_received()` and hands everything else to `publish()`. Fan-out is `on_message_received` (L153–160): `for sub in self._subscriptions.values(): sub.queue.put_nowait(message)` — **every subscriber gets every message**; addressing (`target`) is filtered by the *receiver*, not the bus.
- **Per-subscriber two-tier dispatch.** `BusSubscription` (L27) holds `queue: BusMessageQueue`, `data_queue: asyncio.Queue`, `router_task`, `data_task`. `_router_task` (L169) handles `BusSystemMessage` **inline** and shunts everything else to `data_queue`; `_data_dispatch_task` (L187) drains data sequentially. So every non-system message crosses **two queue hops** before your handler sees it. Subscriber exceptions are swallowed by design (L176–183, L191–200): *"A subscriber exception must not tear down the dispatch task, or the subscriber would silently stop receiving all future messages (including cancel/cleanup). Log and keep going."*
- `BusMessageQueue(asyncio.PriorityQueue)` — `bus/queue.py:18`, `HIGH_PRIORITY = 1` / `LOW_PRIORITY = 2` (L14–15), with monotonic `_high_counter`/`_low_counter` as FIFO tie-breakers. `BusSubscriber` (`bus/subscriber.py:12`) is the whole receive-side contract: a `name` property plus `on_bus_message`. Two lines of interface.
- **Implementations.** `AsyncQueueBus(WorkerBus)` — `bus/local/async_queue.py:15`; `publish()` is literally `self.on_message_received(message)` (L25). `RedisBus` — `bus/network/redis.py:27`, `__init__(self, *, redis: Redis, serializer: MessageSerializer | None = None, channel: str = "pipecat:bus", **kwargs)` (L44–51). `PgmqBus` — `bus/network/pgmq.py:31`, with `DirectPgmqBackend` / `IsolatedPgmqBackend` (the latter over SECURITY DEFINER Postgres wrappers).
- **Serialization is the real boundary.** `JSONMessageSerializer` (`bus/serializers/json.py:28`) handles `_JSON_NATIVE = (str, int, float, bool, type(None))` (L25) plus enums, bytes, dataclasses, and anything with a registered `TypeAdapter` (`bus/adapters/base.py:17`). Default adapters cover only `LLMContext` and `ToolsSchema` (L50–53); extend via `register_adapter(type_, adapter)` (L55). Hence `BusAddWorkerMessage` is local-only — it *"carries an in-memory worker reference that cannot be serialized over the network"* (messages.py L211–212).

### The message taxonomy

`bus/messages.py` (433 L). `BusMessage` (L32) carries only `source: str` and `target: str | None = None` (None = broadcast). Two priority subclasses — `BusDataMessage` (L60), `BusSystemMessage` (L70) — plus a `BusLocalMessage` mixin (L53) meaning "never crosses the network." ~24 concrete types in five groups:

| Group | Types (line) |
|---|---|
| Frame transport | `BusFrameMessage(frame: Frame, direction: FrameDirection, bridge: str \| None)` (86) |
| Pipeline command | `BusTTSSpeakMessage(text, append_to_context=True)` (106) |
| Worker lifecycle | `BusActivateWorkerMessage` (129), `BusDeactivateWorkerMessage` (140), `BusEndMessage` (147), `BusEndWorkerMessage` (161), `BusCancelMessage` (174, *system*), `BusCancelWorkerMessage` (188, *system*) |
| Registry / errors | `BusAddWorkerMessage` (206, system+local), `BusWorkerRegistryMessage` (220), `BusWorkerReadyMessage` (236), `BusWorkerErrorMessage` (259), `BusWorkerLocalErrorMessage` (273, local) |
| Jobs | `BusJobRequestMessage(job_id, job_name, payload)` (292), `BusJobResponseMessage` (307) + `…UrgentMessage` (322), `BusJobUpdateMessage` (340) + urgent twin (353), `BusJobUpdateRequestMessage` (369), `BusJobCancelMessage` (380), `BusJobStream{Start,Data,End}Message` (398/411/424) |

Note the **Urgent twin pattern**: `BusJobResponseMessage` and `BusJobResponseUrgentMessage` are field-identical; the only difference is which base class they extend, i.e. which queue tier they land in.

### What `bridge_processor.py` bridges

- `BusBridgeProcessor(FrameProcessor, BusSubscriber)` — L41, `__init__(self, *, bus: WorkerBus, worker_name: str, target_task: str | None = None, bridge: str | None = None, exclude_frames: tuple[type[Frame], ...] | None = None, **kwargs)` (L49–57). **It consumes the local frame.** The normal path (L114–121) builds a `BusFrameMessage`, calls `await self._bus.send(msg)`, and never calls `push_frame` — so it is a *terminator* mid-pipeline: everything downstream of it receives only what comes *back* from the bus. Only `_LIFECYCLE_FRAMES = (StartFrame, EndFrame, CancelFrame, StopFrame)` (L37), `_PASSTHROUGH_FRAMES = (OutputTransportMessageUrgentFrame,)` (L38), and `exclude_frames` pass through locally. Inbound filtering (L129–148) drops own-source, bridge-name mismatch, `target_task` mismatch, and messages targeted elsewhere. Real usage: `examples/multi-worker/local-handoff/local-handoff-two-agents.py:181` splices it between `aggregators.user()` and `tts` so child workers generate the text the parent speaks.
- `_BusEdgeProcessor(FrameProcessor, BusSubscriber)` — L151, private, installed by `PipelineWorker` when `bridged=` is set. It **tees** instead: `await self.push_frame(frame, direction)` at L206 runs unconditionally *before* the bus send. Inbound arrives via `await self._task.queue_frame(...)` (L236), rationale at L233–235: *"Route via the worker's push queue … so bus inbound serialises with frames the worker queues itself."*
- So: it bridges **pipelines belonging to different workers, at frame granularity.** The payload is an actual `Frame` inside a `BusFrameMessage` envelope. It is a transport for frames, not a state channel.

### Registry and UI

- `WorkerRegistry(runner_name: str)` — `registry/registry.py:19`. Holds `_local_workers: dict[str, WorkerReadyData]`, `_remote_workers: dict[str, dict[str, WorkerReadyData]]`, `_watches: dict[str, list[WatchHandler]]` where `WatchHandler = Callable[[WorkerReadyData], Coroutine]` (L16). `async def watch(self, worker_name: str, handler: WatchHandler) -> None` (L80) is idempotent and **fires immediately if the worker is already registered** (L100–102) — that closes the startup race for free. `async def register(self, worker_data) -> bool` (L104) returns False on duplicates.
- **Expectation check:** `WorkerReadyData` (`registry/types.py:32`) has only **two** fields, `worker_name` and `runner`. `active`/`bridged`/`parent`/`started_at` live on the *snapshot* type `WorkerRegistryEntry` (L13), not on what the registry stores. The registry is a name→locality map, nothing richer.
- `bus/ui/messages.py` carries the UI Worker protocol: `BusUIDataMessage` (L58) base, `BusUIEventMessage(event_name, payload)` (L70) client→server, `BusUICommandMessage(command_name, payload)` (L87) server→client, plus four job-group lifecycle carriers (L111/134/156/179). Its docstring (L14–18) is explicit that these are **not the wire format** — a client-facing worker translates between bus carriers and (e.g.) RTVI frames.

### When to reach for the bus instead of a frame

| Use a **frame** | Use the **bus** |
|---|---|
| Recipient is in the same pipeline | Recipient is a different worker / process |
| Ordering vs. audio/text matters (bus adds 2 queue hops) | Fire-and-forget, order-insensitive |
| Interruption semantics apply (`InterruptionFrame` drains queues; bus messages are **not** drained) | Priority preemption wanted (`BusSystemMessage` jumps queued data) |
| One-way stream | Request/response with a status (`BusJobRequestMessage` → `BusJobResponseMessage`) |

### The two telephony extensions

- **`extensions/ivr/ivr_navigator.py` (473 L)** — outbound: navigate *someone else's* phone tree. `IVRStatus(Enum)` (L43): `DETECTED`/`COMPLETED`/`STUCK`/`WAIT`. `IVRProcessor(FrameProcessor)` (L56), `__init__(self, *, classifier_prompt: str, ivr_prompt: str, ivr_vad_params: VADParams | None = None)` (L70–76), default `VADParams(stop_secs=2.0)` (L87). The mechanism is **XML tags in the LLM's own token stream**, parsed by `PatternPairAggregator` with three pairs registered at L123–132 (`<dtmf>`, `<mode>`, `<ivr>`, all `action=MatchAction.REMOVE`). `<dtmf>N</dtmf>` → `KeypadEntry(value)` → `OutputDTMFUrgentFrame(button=…)` plus a `TextFrame(text=f"<dtmf>{value}</dtmf>")` with `text_frame.skip_tts = True` (L189–194), so the tone is recorded in context but never spoken. The processor **reprograms the LLM upstream of itself**: on `StartFrame` it pushes `LLMMessagesUpdateFrame(messages=[{"role": "developer", "content": classifier_prompt}])` with `FrameDirection.UPSTREAM` (L148–152), and `_handle_ivr_detected` (L258) pushes both `LLMMessagesUpdateFrame(messages=…, run_llm=True)` and `VADParamsUpdateFrame(params=self._ivr_vad_params)` upstream. `IVRNavigator(Pipeline)` (L312) **is a Pipeline**: `super().__init__([self._llm, self._ivr_processor])` (L435). Two ~60-line prompt constants ship in the class: `CLASSIFIER_PROMPT` (L327) and `IVR_NAVIGATION_BASE` (L349, `.format(goal=ivr_prompt)` at L424). Events: `on_conversation_detected`, `on_ivr_status_changed`.
- **`extensions/voicemail/voicemail_detector.py` (720 L)** — outbound: did a human pick up, or a machine? `VoicemailDetector(ParallelPipeline)` (L504), `__init__(self, *, llm: LLMService, voicemail_response_delay: float = 2.0, custom_system_prompt: str | None = None)` (L588–594). Two branches (L651–662): `[self._conversation_gate]` and `[classifier_gate, ctx.user(), classifier_llm, classification_processor, ctx.assistant()]`. Split placement API: `.detector()` (L688, returns `self`) goes after STT; `.gate()` (L699, returns the `TTSGate`) goes after TTS. Parts: `NotifierGate(FrameProcessor)` (L50, `__init__(self, notifier: BaseNotifier, worker_name: str = "gate")`) starts open and closes **permanently** on notify (L109–118); `ClassifierGate` (L121) and `ConversationGate` (L193) subclass it; `ClassificationProcessor` (L214) aggregates `LLMTextFrame` between `LLMFullResponseStartFrame`/`EndFrame` and decides by **substring test on the uppercased buffer** — `if "CONVERSATION" in response` (L353) / `elif "VOICEMAIL" in response` (L361) — then on voicemail calls `await self.broadcast_interruption()` (L370); `TTSGate` (L397) buffers `(TTSStartedFrame, TTSStoppedFrame, TTSTextFrame, TTSAudioRawFrame)` (L466) and either replays in order (L484–487) or **discards** (L500–501). `CLASSIFIER_RESPONSE_INSTRUCTION` (L561) must appear in any custom prompt; `_validate_prompt` (L667) only `logger.warning`s if it is missing — it does not raise.
- **The load-bearing observation for Lina TMR:** `VoicemailDetector.__init__` builds **three `EventNotifier()` objects** — `_gate_notifier`, `_conversation_notifier`, `_voicemail_notifier` (L635–637) — and hands them to four processors sitting in *two different branches and two different points of the outer pipeline*. That is Pipecat's own answer to "non-adjacent components must coordinate," and it is a plain shared object, not the bus.

- **Migration angle:** for boson's rule layers the bus is the **wrong tool for state** and the right tool only for process boundaries. The layers need a *synchronous read of current state*: `SharedLayerContext` (`gateway/layers/context.py:17`) proxies unknown attribute **reads** (`__getattr__`, L40) and **writes** (`__setattr__`, L54) straight through to the live `SessionState`, so a rule evaluating `session.active_stage` gets the current value inline; `AgentStatusTracker.get_status()` (`gateway/layers/status.py:59`) is a poll; `SignalQueue.get_recent(seconds, source_layer)` (`gateway/layers/signals.py:63`) is a query over an append-only list. The bus offers none of those verbs — push-only, two queue hops of staleness, no snapshot. Porting `SharedLayerContext` onto it would force every layer to maintain its own replica and would silently turn `session.counter += 1` (which today writes through to `SessionState`, context.py L54–68) into a write to a local copy. **Correct mapping instead:** (a) keep session state as a shared plain object held by the processors — the `LLMContext` pattern, mutated by the aggregator pair and read synchronously by every holder (see [[llm-service-context]]); (b) express "layer A tells layer B" as shared `EventNotifier`s, exactly as `VoicemailDetector` does; (c) port `SignalQueue` to an **Observer** (`src/pipecat/observers/`, `on_process_frame`/`on_push_frame`) rather than a processor or bus subscriber — observers see every frame at every processor *without being spliced into the pipe*, which is precisely the non-adjacency property boson needs. Reserve the bus for two genuine cases: a classifier/analytics **worker** running out-of-process (`RedisBus`/`PgmqBus` + `BusJobRequestMessage`), and `WorkerRegistry.watch(name, handler)` (registry.py:80) for "wait until component X is ready," whose fire-immediately-if-already-registered semantics boson currently hand-rolls. Both extensions are directly reusable: `VoicemailDetector` is an outbound-dialer requirement Lina TMR has today, and `IVRNavigator` answers "the number we dialed is a phone tree."
