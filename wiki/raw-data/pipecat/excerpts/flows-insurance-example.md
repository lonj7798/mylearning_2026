# Flows by Example — insurance_quote, warm_transfer, patient_intake, restaurant_reservation

<!-- slug: flows-insurance-example · type: source · source: examples/flows/insurance_quote.py (380 L), warm_transfer.py (715 L), patient_intake.py (425 L), restaurant_reservation.py (367 L) -->

**Core Insight.** A Pipecat Flows conversation is not a state *machine* declared up front — it is a graph of **node factory functions** whose edges are the return values of tool calls. `create_quote_results_node(quote)` is a `def`, not a dict, and that is the whole design: collected data is **baked into the next node's prompt by f-string at transition time**, so the node the LLM is about to run is constructed knowing everything gathered so far. There is no separate "memory" component. Three channels carry data forward, and they are used for different purposes: the function's **return value** (visible to the LLM as a tool result), `flow_manager.state` (a plain `dict[str, Any]`, invisible to the LLM, survives context resets), and the **f-string inside `task_messages`** (the only channel that reliably steers the *next* utterance).

**Guideline.** One node = one thing you are trying to extract or accomplish. Put the *objective* in `task_messages` (imperative, addressed to the model, `role: "developer"`) and the *legal moves* in `functions` — a node's function list is your rail guard, so omit `end_conversation` from nodes where hanging up would be wrong. Set `role_message` **once** on the initial node; it persists across transitions until overwritten. Terminal nodes carry `post_actions=[{"type": "end_conversation"}]` and no functions.

## Technical Details

- **The real `insurance_quote.py` node graph.** Five nodes, five factories, four tool edges plus one self-loop:
  ```
  create_initial_node()            --collect_age(age)-------------------> marital_status
  create_marital_status_node()     --collect_marital_status(status)-----> quote_calculation
  create_quote_calculation_node(age, marital_status)
                                   --calculate_quote(age, status)-------> quote_results
  create_quote_results_node(quote) --update_coverage(amount, deductible)-> quote_results  (self-loop)
                                   --end_quote()------------------------> end
  create_end_node()                post_actions=[{"type": "end_conversation"}]
  ```
  Every handler is a **direct function** returning `tuple[Result, NodeConfig]` — e.g. `async def collect_age(flow_manager: FlowManager, age: int) -> tuple[AgeCollectionResult, NodeConfig]` (L114). The schema comes from the docstring; `types.py` requires the first param be named `flow_manager` (`FlowsDirectFunctionWrapper.special_first_param_name()` returns `"flow_manager"`).
- **What goes in `messages` vs `functions` — verbatim.** The whole persona is one string on node 1 (L215): `role_message="You are a friendly insurance agent. Your responses will be converted to audio, so avoid special characters. Always use the available functions to progress the conversation naturally."` Every later node writes only a task: `"Ask about the customer's marital status for premium calculation."` (L233). The terminal-branch node is where the two blend, and it is the most instructive block in the file (L262-281):
  ```python
  def create_quote_results_node(quote) -> NodeConfig:
      return NodeConfig(
          name="quote_results",
          task_messages=[{"role": "developer", "content": (
              f"Quote details:\n"
              f"Monthly Premium: ${quote['monthly_premium']:.2f}\n"
              f"Coverage Amount: ${quote['coverage_amount']:,}\n"
              f"Deductible: ${quote['deductible']:,}\n\n"
              "Explain these quote details to the customer. When they request changes, "
              "use update_coverage to recalculate their quote. Explain how their "
              "changes affected the premium and compare it to their previous quote. ...")}],
          functions=[update_coverage, end_quote],
      )
  ```
  Note the numbers are **pre-formatted in Python**, not left to the model — a voice-agent discipline (the model never says "one hundred fifty point zero").
- **The data-threading round trip, exactly as written.** `collect_age` does `flow_manager.state["age"] = age` (L124) — the only `state` write in the file. `collect_marital_status` reads it back to build the next node: `create_quote_calculation_node(flow_manager.state["age"], marital_status)` (L144). That factory then interpolates it into the prompt: `f"Calculate a quote for {age} year old {marital_status} customer. First, call calculate_quote with their information."` (L248-249) — and `calculate_quote(flow_manager, age, marital_status)` receives them **as LLM-supplied arguments again**. So a known value travels `state → prompt → model → function args`. It works, but it is a real round trip through the model, not a direct read; for anything the model must not paraphrase (a Korean 주민등록번호, a policy code), read from `state` inside the handler instead of declaring it as a parameter.
- **`patient_intake.py` — structured capture at scale.** Same shape, but collection functions take **list-of-dict** parameters described entirely in the docstring, e.g. `record_prescriptions(flow_manager, prescriptions: list[dict])` with `Args: prescriptions (list[dict]): List of prescription objects, each with "medication" (str, ...) and "dosage" (str, ...)` (L142-148). Each returns only a count (`PrescriptionRecordResult(count=len(prescriptions))`) while the payload goes to `flow_manager.state["prescriptions"]` — **the LLM gets an acknowledgement, the app gets the data.** Two backward/branching edges exist: `revise_information` returns `create_prescriptions_node()` (a loop back), `confirm_information` returns `create_confirmation_node()`. Context is managed per node: `get_prescriptions` uses `ContextStrategyConfig(strategy=ContextStrategy.RESET)` (L244) and re-declares `role_message` because of it; `verify` uses `RESET_WITH_SUMMARY` with a domain-specific `summary_prompt` (L306-313). Docstrings double as routing hints: *"Once confirmed, the next step is to collect allergy information."*
- **`restaurant_reservation.py` — outcome branching and inbound/outbound.** `check_availability` returns a *different* node depending on the API result (L161-164): `create_confirmation_node()` or `create_no_availability_node(alternative_times)`, the latter closing over the data with `times_list = ", ".join(alternative_times)` (L227). Rail-guarding is explicit in prose: `"This is your only job for now; if the customer asks for something else, politely remind them you can't do it."` (L183). `create_initial_node(wait_for_user)` sets `respond_immediately=not wait_for_user` (L187) — the one-flag switch between an outbound call (bot speaks first) and inbound (bot waits).
- **`warm_transfer.py` — human handoff, and the one transition that is *not* a tool call.** The 5-node graph is documented in a header comment block (L82-120): `initial_customer_interaction` → `continued_customer_interaction` | `transferring_to_human_agent` → `human_agent_interaction` → `end_human_agent_conversation`. Two mechanisms matter for sales:
  1. **Outcome-routed handoff.** `next_node_after_customer_task(result)` (L250) is a plain helper: `if result.get("status") == "success": return create_continued_customer_interaction_node() else: return create_transferring_to_human_agent_node()`. Escalation is just the failure branch of every task function.
  2. **Event-driven transition.** The agent joining is not a tool call, so the transition is pushed from a transport event handler (L650-658): `if user_id == "agent" and flow_manager.current_node == "transferring_to_human_agent": await flow_manager.set_node_from_config(create_human_agent_interaction_node())`. Note the guard on `flow_manager.current_node` — the only concurrency control there is.
  The hold node is pure side effect, with **no functions at all** (L325-341): `pre_actions=[ActionConfig(type="function", handler=mute_customer)]`, `post_actions=[start_hold_music, make_customer_hear_only_hold_music, print_human_agent_join_url]` — see [[flows-actions]] for why `function` is the only action type worth using. And the briefing node hands the human a summary rather than the transcript, via `ContextStrategyConfig(strategy=ContextStrategy.RESET_WITH_SUMMARY, summary_prompt="Summarize the conversation with the customer, including what they were trying to accomplish and what, if anything, went wrong ... Include specific error details.")` (L360-365).
- **Migration angle:** `agents/test-lina-gateway/stage_config.py` (86 L) already *is* this graph, in declarative form — `stages = {"introduction": {...}, "product_focused": {...}, "consultation": {...}, "purchase": {...}, "informed_consent": {...}, "reschedule": {...}, "dnc_processing": {...}, "escalate_to_human": {...}, "end": {...}}`, each with `tools`, `skills`, and `transitions`. The port is mechanical for two of the three fields and a genuine rewrite for the third:
  - `stages[X]["tools"]` → `NodeConfig["functions"]`. Direct. `_GLOBAL_TOOLS` (currently `[]`) → `FlowManager(global_functions=[...])`, which Flows mixes in at every node: `functions_list = self._global_functions + node_config.get("functions", [])` (`manager.py:654`).
  - `stages[X]["transitions"]` → **stops being data.** In Flows the legal successors are implicit in which `NodeConfig` each function can return, so the stage machine's rejection path disappears — and with it the class of bug the config file documents twice (`v0.7.5 (#12): "purchase" added — transition_detector.py:157 emits StageTransition("purchase") ... but the stage machine rejected it because this list omitted "purchase"`). That bug is structurally impossible in Flows; the trade is that you lose the single-file readable transition table.
  - `stages[X]["skills"]` (`product_manager`, `payment_manager`) → no Flows concept. Either flatten to functions, or keep as boson meta-tools behind a `use_skill` direct function ([[boson-tool-router]]).
  - **The hard part:** Lina's transitions are emitted by `transition_detector.py` rules watching the *user's* utterance, not by the model choosing a tool. Flows has exactly one non-tool transition path — `flow_manager.set_node_from_config(...)` called from an event handler, as `warm_transfer.py:658` does. So each rule becomes an upstream `FrameProcessor` that inspects the transcription and calls `set_node_from_config`, guarded on `flow_manager.current_node` the same way. `escalate_to_human` maps onto the full `warm_transfer.py` recipe (mute via `update_remote_participants`, hold music subprocess, `RESET_WITH_SUMMARY` briefing) — that file is the closest thing in the repo to a shippable feature for TMR. `informed_consent`'s four Korean consent questions (개인정보 수집·이용, 신용정보집중기관 조회, 주민번호 처리, 건강정보 처리) are the `patient_intake.py` pattern verbatim: one node per question or one node with a `record_consent(consent_item, agreed)` function looping back to itself, `state` accumulating the answers, and a `RESET_WITH_SUMMARY` verification node before `purchase`. `dnc_processing` and `end` are terminal nodes with `post_actions=[{"type": "end_conversation"}]`.
